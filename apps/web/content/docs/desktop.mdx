`celestia-ui` is the desktop counterpart of `@celestia-project/ui`: a Rust component library for
native desktop apps built on [GPUI](https://gpui.rs) (`gpui-pre` 0.3.6) **directly** — the two
widget layers it wraps, `gpui-base` and `gpui-component` 0.6.6, are named as themselves, so every
import states the crate it comes from. The shape mirrors the web package: `packages/ui` wraps Base
UI primitives with celestia tokens; `celestia-ui` wraps the gpui-component library the same way, so
most web files map 1:1 onto a desktop module (`drawer.tsx` → `sheet`, `toast.tsx` → `notification`,
`file-tree.tsx` → `tree`).

</Callout>

## Running it

Rust **≥ 1.97** (edition 2024); no environment variables — the theme JSON is compile-time
embedded. macOS needs no extra toolchain, Linux needs Vulkan + Wayland/X11/fontconfig headers,
Windows needs MSVC.

```bash
pnpm desktop                        # from the repo root — build & open the gallery window
cargo run -p celestia-desktop       # or directly from packages/desktop/  (⌘D / Ctrl+D toggles theme)
cargo test --workspace              # unit + gpui TestAppContext tests (theme pins live here)
```

## Architecture

One file per component, split into two category modules mirroring
`packages/ui/src/components/{primitive,composite}`:

1. **Celestia wrappers** — components with a shadcn-shaped prop surface that
   render `gpui-component` primitives under Celestia theming: `button.rs` (`Button` +
   `ButtonVariant` — primary/secondary/destructive/outline/ghost/quiet/link, plus
   desktop-only `success`/`warning`/`info` status fills — with `ButtonSize`'s five
   height steps and four icon steps, `leading_icon`/`trailing_icon` slots, the
   `Button::icon` constructor, and a `loading` state that swaps the leading slot for
   a `Spinner`), `badge.rs` (`Badge` + `BadgeVariant` — composed from a plain
   `div` rather than `gpui-component`'s `Tag`, because the web status variants are a 10%
   tint of the accent under accent-coloured text and the Tag paints solid fills
   plus a hover dim the web does not have), `avatar.rs` (`Avatar` +
   `AvatarSize`, the web's 24/32/40px scale), `card.rs`, `section_heading.rs`,
   `text_editor.rs` and `code_editor.rs`.
2. **Per-component re-exports** — the remaining components each get a file
   (`switch.rs`, `popover.rs`, `table.rs`, …) re-exporting the matching
   gpui-component API, with a doc comment recording the web-file → desktop
   mapping (the table below). Wrapper types are also flattened at
   `celestia_ui::components::*` (e.g. `components::Button`); module-only
   components are reached through their category-qualified path
   (`components::primitive::table::…`, `components::composite::sidebar::…`).
3. **Raw-GPUI components** — written directly on `gpui` (`gpui-pre`) and
   importing nothing from `gpui_component`: `primitive/alert.rs`,
   `primitive/progress.rs`, `primitive/skeleton.rs`, `primitive/spinner.rs`,
   `primitive/shimmer.rs`, `primitive/icon.rs`, `primitive/badge.rs`,
   `primitive/label.rs`, `primitive/rating.rs`, `composite/loaders.rs`,
   `composite/notice.rs`, `composite/context_badge.rs`. They render with
   `gpui::div` / `gpui::svg` / `gpui::canvas` and read colors from `cx.theme()`.

### Dependency layers

There is **no facade crate**. `celestia-ui` depends on the framework and its two
widget layers directly, so every import names the crate it actually comes from:

| Layer     | Crate            | Used for                                                                                     |
| --------- | ---------------- | -------------------------------------------------------------------------------------------- |
| Framework | `gpui` (`gpui-pre`) | everything a component draws                                                                 |
| Base      | `gpui-base`      | **the inner component library** (`Checkbox`, `Popover`, `Tree`, `Resizable`, `Slider`, `Tabs`, `Table`, the motion stack, scroll) plus the free style helpers (`h_flex` / `v_flex`, `StyledExt`, `RoleOverride`, `box_shadow`) |
| Widgets   | `gpui-component` | a thin styling layer *over* `gpui-base`; the styled controls a file still re-exports                     |

Components move from (2) → (3) one **family** at a time, and
`crates/ui/src/components/mod.rs` tracks what is done. Rewritten so far:

- **Feedback** — `primitive/`: `alert`, `progress`, `skeleton`, `spinner`,
  `shimmer`, `icon`; `composite/`: `loaders`, `notice`, `context_badge`.
- **Structural** — `primitive/`: `separator`, `kbd`, `link`, `breadcrumb`;
  `composite/`: `group_box`, `status_bar`, `title_bar`, `description_list`,
  `empty`.
- **Display** — `primitive/`: `badge`, `label`, `rating`.
- **Layout** — `primitive/`: `card`; `composite/`: `section_heading`,
  `sidebar_layout`, and the SwiftUI vocabulary `h_stack`, `v_stack`, `z_stack`,
  `spacer`, `scroll_view`, `v_grid`, `frame`, `alignment`.
- **Conversation** — `primitive/`: `bubble`; `composite/`: `message`, `marker`.
  (`message_scroller` is split out and still a shim — it is the one part of the
  conversation stack sitting on `gpui-base` motion and scroll.)

Pick the next family by **transitive cost, not file size**, measured on two axes.
First, what the target's own imports drag in: the question is not "how big is it"
but "does the closure reach a `gpui-base` **state machine**". `StyledExt`,
`h_flex` / `v_flex`, `RoleOverride` and the sizing traits are *style helpers* and
cost nothing to inline; `Checkbox`, `Slider`, `Popover`, `Tree`, `ResizableState`
and the motion stack are *state machines* and have to be reimplemented. Second,
who else imports it: `bubble` and `message` import each other (`MessageContent::bubble`
takes the crate's own `Bubble`), so they move together, and `menu` is imported by
ten upstream modules.

34 shims remain, and exactly one of them is still free. `attachment` (1017
upstream lines) references `gpui_base` **not once** — it draws from `gpui` plus
the free style helpers, and its only component dependency, `shimmer`, is already
migrated. `title_bar` was the other one; it is done. Everything else names at
least one `gpui-base` module directly, and the large ones close over ~45k
upstream lines each — for those the base layer is the next milestone, not another
component batch. (`resizable` is the one the analyzer cannot rank: it reports a
zero because `gpui_component::resizable` is an inline `pub mod` over `gpui-base`
rather than a file. A name that resolves to nothing is a red flag, not a cheap
target.)

Two things make that measurement reproducible rather than remembered.
`scripts/ui-audit/gpui-migration-cost.py` resolves each shim's target module and
reports a **`gb1`** column — the `gpui-base` modules the target's *own* files
import, at depth 1. Read `gb1`, not the closure columns: a closure total
saturates at ~45k lines for nearly every shim *and* over-reaches (`stepper`'s
closure claims `markdown_ext`, `number_input` and `virtual_list`, which a stepper
plainly does not use). Depth 1 cannot be inflated transitively, so `gb1 == 0`
means a one-file port and nothing else does.

And a correction that reframes the whole remaining list: **`gpui-base` is not a
helper crate, it is the inner component library.** `gpui-component` is a thin
styling layer over it — upstream `checkbox.rs` is a struct holding
`base: gpui_base::Checkbox`, and `popover.rs` does
`use gpui_base::Popover as BasePopover`. Only the pure style helpers re-exported
through it (`h_flex` / `v_flex`, `StyledExt`, `RoleOverride`, `FocusableExt`,
`box_shadow`, `AxisExt`, `LengthExt`, `Edges`, `Placement`, `Side`, `Measure`)
are free to inline, which is why `title_bar` — zero of them — was cheap.

The substitutions that recur, and the two places the old facade was load-bearing:

| Was (`gpui-kit` facade) | Now |
| --- | --- |
| `use gpui_kit::{div, px, …}` | `use gpui::{div, px, …}` — same items, so mostly mechanical |
| `use gpui_kit::component::ActiveTheme` | `use crate::theme::ActiveTheme as _` |
| `gpui_kit::component::Icon` / `assets::IconName` | `crate::components::primitive::icon::{Phosphor, PhosphorIcon}` |
| `IconName::StarFill` | `Phosphor::new(PhosphorIcon::Star).weight(PhosphorWeight::Fill)` |
| `.refine_style(&style)` | `el.style().refine(&style)` |
| `h_flex()` / `v_flex()` | `div().flex().flex_row()` / `div().flex().flex_col()`, **plus the cross-axis rule the helper supplied** — `h_flex()` is `.items_center()`, so a row that relied on it keeps an explicit `.items_center()` |
| `Tooltip::new(..).build(..)` | `.tooltip(\|_, cx\| cx.new(\|_\| MyHint).into())` |
| `Sizable` / `Size` | a crate-local metric bucket, e.g. `DescriptionListSize`, `RatingSize`, `GpuiBadgeSize` |

`refine_style` and the `h_flex`/`v_flex` helpers are **gpui-base**, not core
gpui, so a migrated file spells out `style().refine(..)` and the flex
direction. Two further traps: `ParentElement` must be imported **by name**
(not `as _`) if the file implements it, and `Styled` / `InteractiveElement` /
`Refineable` must be in scope or `h_4` / `child` / `id` / `refine` silently
fail to resolve. A third: a facade enum that derives `Clone` may not survive the
port — widening one arm to hold an `AnyElement` (not `Clone`) means dropping the
derive, not boxing around it. The full recipe — and how to pick the next family
by *transitive* cost rather than file size — is the module doc of
`crates/ui/src/components/mod.rs`. The theme service (`cx.theme()` →
`gpui-component`'s `Theme`/`ThemeColor`) is the last piece scheduled to move; it
is re-exported from `crate::theme` so component files never name
`gpui_component` directly.

One rule runs through everything: **raw hex lives only in `theme.json` and `palette.rs`**. Call
sites take colors by role through `cx.theme()` (semantic roles: background, foreground, primary,
border, sidebar…) or `palette(cx)` (brand + charts).

## Component map

Every component lives in `crates/ui/src/components/`, under one of two
categories that mirror `packages/ui/src/components/{primitive,composite}`:

- **`primitive/`** — one control, or one visual atom, per file.
- **`composite/`** — surfaces assembled from several primitives, plus
  application-level assemblies (chrome, shells, editors).

The split is by **composition, not size**: a file that renders two or more
primitives, or that owns a layout region rather than a control, is a composite.

### Button

`Button` is the one component that goes past its web counterpart, so its extra surface is worth
spelling out.

**Sizes** are web's height ladder plus its icon ladder, in one place:

| Step | Web | Height | Padding | Gap | Text | Icon |
| ---- | --- | ------ | ------- | --- | ---- | ---- |
| `XSmall` | `xs` | 20px | 8px | 4px | 10px | 10px |
| `Small` | `sm` | 24px | 10px | 4px | 12px | 12px |
| `Medium` *(default)* | `default` | 26px | 12px | 6px | 12px | 14px |
| `Md` | `md` | 28px | 10px | 4px | 12px | 12px |
| `Large` | `lg` | 36px | 14px | 8px | 14px | 16px |
| `Icon` | `icon` | 32px square | — | — | 12px | 14px |
| `IconXs` / `IconSm` / `IconLg` | `icon-xs` / `icon-sm` / `icon-lg` | 20 / 24 / 36px square | — | — | 10 / 12 / 14px | 10 / 12 / 16px |

`Md` and `Medium` are **different steps** — web's `default` and `md` are not the same thing. The
icon column is deliberately non-monotonic: `Md` is `sm` with one more step of height and nothing
else changed, so the taller button keeps the smaller icon. `Large` is the one deliberate
deviation — web's `lg` is 36px but keeps `text-xs` and `gap-1.5`; the desktop widens both.

**Variants** are the web set (`primary` / `secondary` / `destructive` / `outline` / `ghost` /
`quiet` / `link`) plus three desktop-only status fills — `Success`, `Warning`, `Info` — which
complete the set `alert.rs` and `badge.rs` already carry. All four status variants share one
recipe: the accent is the surface *and* the border, the paired `*_foreground` token is the text,
and the 3D edge is the accent darkened toward black.

**Icon slots and loading** are typed rather than assembled by hand:

```rust
use celestia_ui::components::primitive::button::{Button, ButtonSize, ButtonVariant};
use celestia_ui::components::primitive::icon::PhosphorIcon;

// Leading / trailing slots — a bare PhosphorIcon renders at the size step's
// icon size and inherits the button's text colour, so it follows the hover
// fade and the disabled dimming for free.
Button::new("export")
    .variant(ButtonVariant::Outline)
    .leading_icon(PhosphorIcon::DownloadSimple)
    .trailing_icon(PhosphorIcon::CaretDown)
    .label("Export");

// Icon-only: the `icon` constructor defaults to `ButtonSize::Icon`.
Button::icon("settings", PhosphorIcon::Gear);

// Loading: the spinner takes the *leading slot* rather than being pushed in
// front of it, so the label and the trailing icon keep their positions and the
// button does not reflow. Interaction is blocked, but the fill, the elevation
// and the opacity are kept — a loading button is busy, not forbidden.
Button::new("save")
    .variant(ButtonVariant::Primary)
    .loading(true)
    .label("Saving");
```

Two GPUI-specific notes on the icon ladder. Web expresses it with a descendant selector
(`[&_svg:not([class*='size-'])]:size-3.5`); GPUI has no descendant styling, so the slot is an
explicit wrapper whose `text_size` a bare `PhosphorIcon` inherits — an icon that carries its own
explicit size still wins, which is what web's `:not([class*='size-'])` guard buys. And
`Button::icon_size` is the escape hatch for a glyph whose proportions need another step.

`CursorStyle` has no wait/progress variant, so a loading button keeps the plain arrow cursor;
`OperationNotAllowed` is the *disabled* signal and would read as a broken control.

### TitleBar

The window chrome is desktop-only, so `TitleBar` is a port of `gpui-component`'s rather than
of a web component. It is the cheapest kind of port — upstream's file reaches **zero**
`gpui-base` components, so nothing had to be reimplemented on its behalf.

Use it as the first child of the window's root view, and start the window from
`TitleBar::window_options()`:

```rust
use celestia_ui::components::composite::title_bar::TitleBar;
use celestia_ui::gpui::WindowOptions;

let options = WindowOptions {
    window_min_size: None,
    ..TitleBar::window_options()   // app_owns_titlebar_drag: true
};
```

`window_options()` sets `app_owns_titlebar_drag: true` deliberately. The bar moves the window
itself via `start_window_move`, so AppKit must not also treat it as a system window-move
region — otherwise macOS handles double clicks on its own *in addition* to ours and delays
every title bar click while it disambiguates.

Four deviations from the upstream file, all marked `DEV:` in the source:

- **Caption glyphs.** Upstream's `IconName::WindowMinimize` / `WindowRestore` / `WindowMaximize`
  / `WindowClose` are not in the Phosphor catalog, so they map to the closest Phosphor shapes:
  `Minus`, `CopySimple`, `Square`, `X`.
- **`Vec` in place of `SmallVec<[AnyElement; 1]>`** — one inline slot is not worth a new direct
  dependency.
- **No `Render` impl on the drag state.** Upstream carries an empty one with a "remove this when
  GPUI has released v0.2.3" TODO; `Window::use_state<S: 'static>` places no such bound.
- **The real `ClickEvent` is passed to the close callback** instead of a synthesized
  `ClickEvent::default()`.

Two upstream helpers were inlined rather than ported: `on_double_click` is `on_click` plus a
`click_count() == 2` guard, and `Icon::new(..).small()` resolves to a 14px glyph, which is
`Phosphor::new(icon).size(px(14.0))` here.

The caption cluster is platform-conditional and worth knowing about: it renders nothing on
macOS (the traffic lights are the OS's) or in the browser, and on Linux it stands down entirely
when `window.window_decorations()` is not `Decorations::Client` — under server-side decorations
the window manager already draws min/max/close, so ours would stack a duplicate pair on top,
most visibly two close buttons.

## Zeron-port primitives

A first family of primitives is ported from the Zeron reference (`reference/zeron`, a GPUI chat
app). These are celestia-native APIs — colors resolve from `cx.theme()` / `palette(cx)`, never
from zeron's theme — and all motion runs through one shared module:

- `celestia_ui::motion` — the animation kit: CSS-exact `CubicBezier` curves, a `MotionSpec`
  catalog (`FADE_IN`, `MENU_IN`, `DIALOG_IN`, `PULSE`, `GRADIENT_SPIN`, …) with entrance helpers
  (`fade_in`, `menu_in`, `dialog_in`), premultiplied-sRGB `mix`, and the **pulse clock**: a shared
  ~30fps driver that keeps every mounted loader phase-locked and parks entirely once the last one
  unmounts (a window with no spinner schedules nothing). Reduced motion (gpui's
  `reduce_motion` flag) snaps loaders to a static rest brightness and zeroes the wave phases.
- `components/loaders.rs` — the cell loaders: `pulse_loader` (5-cell opacity/scale wave),
  `gradient_spinner` (3×3 grid on the `brand → brand_deep` ramp, the pulse travels
  bottom-edge → top-centre), `mini_spinner` / `mini_mono_spinner` (2×3 radial chase in a
  self-contained view), and `progress_ring` (stroked-polyline radial percent, works over dimmed
  imagery with a white tint).
- `components/notice.rs` — `notice_chip`: the tinted failure card (accent wash + border, alert
  triangle, copy-to-clipboard button, wrapping message — never truncating stderr), `Plain`
  (inline) and `Tile` (block) icon treatments, danger/warning palettes.
- `components/context_badge.rs` — `MessageBadge` pills with `BadgeDetail` rows: a 24px chip that
  lifts a hover card of location/tag/body rows after a 280ms hover delay. The three slots are
  generic — the module never learns what the context cites.

The gallery's **Feedback** section renders all of them live.

<Callout type="warn" title="What could not be ported from Zeron">
  Zeron does not run stock gpui — it builds on its fork `zeronsh/zui` (checked
  out at `reference/zui`), which adds renderer-level primitives: `BackdropBlur`
  (frosted glass), per-pixel `EdgeFade` / `Window::with_edge_fade` (scroll-edge
  fades), transparent-window compositing and image corner-radius masks.
  the pinned `gpui` (the `gpui-pre` series) has none of these, so zeron's
  `frost.rs`, `glass.rs` and `edge_fade.rs` stay unported — adopting them would
  mean replacing the whole pinned stack with the fork. Everything built
  on the shared core API (div/Styled, `Animation`, `canvas`, element state)
  ports cleanly, which is the family above.
</Callout>

## Motion

`celestia_ui::motion` has two layers, and it is worth knowing which one a given
component is on.

**1. The design-system token layer.** The same curves and durations the web
primitives use, ported from `@theme` in `packages/ui/src/styles/globals.css`:

| Token                  | Value                                  | Used for                                              |
| ---------------------- | -------------------------------------- | ----------------------------------------------------- |
| `EASE_OUT_TOKEN`       | `cubic-bezier(0.23, 1, 0.32, 1)`       | the signature curve — hovers, indicator, entrances    |
| `EASE_IN_OUT_TOKEN`    | `cubic-bezier(0.77, 0, 0.175, 1)`      | deliberate moves                                      |
| `EASE_DRAWER_TOKEN`    | `cubic-bezier(0.32, 0.72, 0, 1)`       | sheets, drawers, the overlay scrim                    |
| `DURATION_INSTANT`     | 80ms                                   | press feedback (`active:*`)                           |
| `DURATION_FAST`        | 150ms                                  | hover colour and background fades                     |
| `DURATION_NORMAL`      | 220ms                                  | the tabs indicator, panel entrances                   |
| `DURATION_SLOW`        | 320ms                                  | sheets, navigation menus, toasts                      |
| `DURATION_SLOWER`      | 500ms                                  | caret blink, long reveals                             |

They are exposed three ways. Named `MotionSpec`s (`HOVER`, `SLIDE`, `PRESS`,
`POPUP_IN`, `OVERLAY`) let a component name the effect it is reproducing;
`spec_transition(spec)` (and the `hover_transition` / `press_transition` /
`slide_transition` shorthands) turn one into a `gpui_base` value-transition
policy for `transition-colors`-style fades; and `motion_tokens()` packages the
whole scale as `gpui-component`'s `MotionTokens`.

```rust
// `transition-colors duration-fast ease-out` — a hover fade between two states.
let t = transition(("btn-hover", self.id.clone()), hovered as u8 as f32,
                   motion::hover_transition(), window, cx);
let bg = motion::mix(rest, hover, t);
```

`theme.json` **cannot** carry this scale — `gpui-component`'s `Theme::motion` is
`#[serde(skip)]` — so `theme::install` assigns it directly. That one assignment
is what re-times every re-exported `gpui-component` component (switch, checkbox, slider,
accordion, collapsible, progress, carousel, `TabBar`) off `gpui-component`'s own
0/120/180/280ms ladder and onto the design system's 80/150/220/320ms. Because
`apply_config` never touches the field, it survives `Theme::change` and
system-appearance switches.

Colour blending goes through `motion::mix`, which interpolates component-wise in
sRGB with premultiplied alpha — the way a browser transitions a colour — so a
wash fading in from transparent brightens rather than passing through grey.

**2. The Zeron catalogue.** The entrances and the loader pulse clock described
under [Zeron-port primitives](#zeron-port-primitives) below are a separate,
older layer: Zeron's own curves (`EASE_OUT_EXPO`, `EASE`, …) and periods
(`PULSE`, `GRADIENT_SPIN`). They have no web-primitive counterpart to match and
were deliberately left alone.

### Focus rings

Every focus ring is **2px at full strength** — `focus-visible:ring-2
focus-visible:ring-ring`, enforced on the web by
`scripts/ui-audit/focus-rings.mjs`. `gpui-component`'s own `focus_ring_style` draws 3px
at 50% opacity, which that rule forbids, so `celestia_ui::focus_ring::focus_ring`
is an in-crate replacement: it reads the element's own border widths and corner
radii, adds 2px, and attaches an absolutely-positioned bordered child at
`-inset` coloured `cx.theme().ring` with no alpha.

### What GPUI cannot animate

**GPUI has no element transform** — only images and SVGs take a
`TransformationMatrix`, so there is nothing to scale a subtree with. Two web
effects therefore cannot be reproduced literally:

- `active:scale-[0.97]` on a tab trigger. The desktop keeps the web's *colour*
  behaviour (no colour change beyond hover) and drops only the geometry.
- `zoom-in-[0.99]` on the tabs panel entrance. The 1% zoom is approximated by a
  2px rise, which reads the same on a panel edge.

gpui-component documents the same constraint for the dropdown entrance in its
`popover.rs`. Anything built on the shared core API — `div`/`Styled`,
`Animation`, `canvas`, element state — ports cleanly; only the renderer-level
extras do not.

The component-by-component audit that produced this layer, including the
per-wrapper parity tables and the deliberate non-goals, lives at
`packages/desktop/AUDIT-component-motion.md`.

## Layout stacks — SwiftUI vocabulary

`components/composite/` carries SwiftUI's layout vocabulary — one file per
construct, no web counterpart. Each is a thin `RenderOnce` wrapper over a gpui
flex row / column / layer, so they compose with every other component in the
library:

| Component | Maps to | Notes |
| --- | --- | --- |
| `HStack` | `HStack(alignment:spacing:)` | flex row; `spacing` becomes the flex gap (default 8px); alignment is the vertical cross axis (`Top` / `Center` / `Bottom`) |
| `VStack` | `VStack(alignment:spacing:)` | flex column; defaults `Leading` / 8px; alignment is the horizontal cross axis (`Leading` / `Center` / `Trailing`) |
| `Spacer` | `Spacer(minLength:)` | expands along the parent stack's main axis; `min_length` floors BOTH axes (min-width and min-height) |
| `ZStack` | `ZStack(alignment:)` | every child becomes an absolutely-positioned full-bleed layer; the single alignment pins all layers; fills its parent, so give it a bounded frame |
| `VGrid` | `LazyVGrid(columns:spacing:)` | children chunk into rows sized by `GridItem::Fixed(px(...))` / `GridItem::Flexible` rules; rows wrap in child order; spacing applies between rows and columns |

```rust
use celestia_ui::components::composite::alignment::{
    HorizontalAlignment, VerticalAlignment, ZAlignment,
};
use celestia_ui::components::composite::h_stack::HStack;
use celestia_ui::components::composite::spacer::Spacer;
use celestia_ui::components::composite::v_grid::{GridItem, VGrid};
use celestia_ui::components::composite::v_stack::VStack;
use celestia_ui::components::composite::z_stack::ZStack;

// Toolbar idiom: content leading, actions trailing, Spacer in between.
HStack::new(VerticalAlignment::Center).spacing(px(8.))
    .child(title)
    .child(Spacer::new())
    .child(Button::new("act").label("Action"))

// One alignment pins every ZStack layer; compose a layer (an inner
// HStack) to place content on independent edges.
ZStack::new(ZAlignment::BottomTrailing)
    .child(div().size_full().bg(photo))
    .child(
        div().w_full().p_3().child(
            HStack::new(VerticalAlignment::Bottom)
                .child(caption)
                .child(Spacer::new())
                .child(badge),
        ),
    )

// Column rules: Fixed pins a width, Flexible shares what's left.
VGrid::new([GridItem::Fixed(px(88.)), GridItem::Flexible, GridItem::Flexible])
    .spacing(px(8.))
    .children(cards)
```

Three gotchas worth internalizing:

- **The stacks are layout-only** — they implement `ParentElement` but not
  `Styled`, so there is no `HStack::new(..).p_3()`. Wrap them in a plain
  `div()` for width, padding, or background.
- **ZStack is always full-bleed.** Its root is `relative size_full` and each
  child is wrapped in an `absolute inset-0` layer, so a ZStack inside an
  unsized container collapses. Put a real frame (`h(px(..))` / `size_full`)
  under it.
- **VGrid grows vertically** — wrap long content in a `ScrollView` (the axis
  `ScrollView` lives beside it in `composite/`).

The gallery's **Layout** section (`crates/showcase/src/sections/layout.rs`)
renders every alignment variant of all three stacks live, states the defaults
and gotchas in each card's footer, and ships an interactive playground: pick
the axis (row / column / depth), alignment, spacing, and child count, and the
preview plus the exact constructor snippet update together.

## Icons — Phosphor

`crates/ui/src/components/primitive/icon.rs` ships the **Phosphor** icon set (Phosphor Core 2.1.1, MIT —
license vendored at `assets/phosphor/LICENSE-PHOSPHOR`). The upstream
[`gpui-phosphor`](https://docs.rs/gpui-phosphor) crate can't be used directly — it targets the
`gpui` 0.2 lineage and can't link against the pinned `gpui-pre` types — so the approach is ported
onto this stack instead:

- **SVGs** — 1,512 glyphs × 3 weights (`regular`, `bold`, `fill`) vendored under
  `crates/ui/assets/phosphor/<weight>/<name>.svg`. Duotone is skipped: GPUI's SVG renderer paints
  every path with one color, so duotone would render as solid.
- **`PhosphorIcon`** — a typed catalog enum generated by `crates/ui/build.rs` at compile time
  (`PhosphorIcon::Heart`, `PhosphorIcon::PaperPlaneTilt`, …, plus `ALL` / `COUNT` / `name()`).
  It renders through a plain `gpui::svg` — no third-party icon component sits in between — and
  bare `.child(PhosphorIcon::Heart)` renders at the surrounding text style, regular weight.
- **`Phosphor`** — the weight-aware wrapper (the counterpart of gpui-phosphor's `Icon` builder):
  `Phosphor::new(PhosphorIcon::Heart).weight(PhosphorWeight::Fill).size(px(20.)).color(…)`.
  Size and color default to the surrounding text style. The weight is just the asset-path prefix
  (`phosphor/<weight>/<name>.svg`), so every enum variant exists at every embedded weight.

```bash
cargo test --workspace   # asset-source tests: every glyph resolves at every weight
```

### Asset source registration (required)

gpui takes a **single asset source at startup**. Register the composite from
`celestia_ui::assets` in `main` — it serves the vendored Phosphor SVGs and
reports every other path as a clean miss:

```rust
use celestia_ui::assets::CelestiaAssets;

gpui_platform::application()
    .with_assets(CelestiaAssets)          // phosphor/…
    .run(|cx| { /* … */ });
```

Without a registered source gpui's fallback serves nothing and **every icon renders blank
silently** — `CelestiaAssets` fixes it. Phosphor is the only catalog: the crate used to fall
through to a bundled Lucide set, which was dropped once the three Lucide glyphs still in use
(a tab's `BookOpen`, the showcase's `Eye` and `Code`) proved to have direct Phosphor
equivalents. The gallery's **Phosphor Icons** section
(`crates/showcase/src/sections/icons.rs`) renders the full catalog with live search, a
Regular/Bold/Fill weight switcher, and click-to-copy `PhosphorIcon::…` names.

An application can layer its own media on top the same way: embed a folder with
`rust_embed` and wrap `CelestiaAssets` as the fallback. The showcase does exactly this —
`crates/showcase/src/assets.rs` embeds its demo avatars (`assets/avatars/**`, used by the
chat section's image `Avatar`s) and registers a `ShowcaseAssets` that checks the demo
media first, then falls through to `CelestiaAssets`.

## Theming

`crates/ui/src/theme.json` is the sRGB-hex port of
`packages/ui/src/styles/globals.css` — the web CSS file stays the single source of truth, and the
JSON is re-derived from it when tokens change (grays via OKLab → linear sRGB = L³, chromatic
tokens through full OKLab → sRGB with gamut clamping, alpha tokens as 8-digit hex). `init()` loads
the JSON into the `ThemeRegistry` and **replaces** `gpui-component`'s default light/dark configs, so
`Theme::change` and system-appearance sync keep using the Celestia palettes with no re-patching.

Key values are pinned by `cargo test --workspace`: light `primary` `#d40c1a`, dark `#ff4d46`
(out-of-gamut `oklch(0.68 0.22 27)` clipped), the dark border as white-alpha, `selection` always
primary at 22%, and a guard test that fails if primary ever regresses to the retired brand blue.
Beyond the semantic roles, `palette(cx)` carries the mode-independent product colors — `brand`
`#dc2626`, `brand_deep` `#b51230`, `brand_foreground` and the grayscale chart ramp — mirroring the
web where these live once on `:root`.

### Global theme config

`theme.json` is the compiled-in default; the runtime knob over it is
**`celestia_ui::theme::AppTheme`** (`crates/ui/src/theme/config.rs`) — the desktop counterpart of
the shadcn `:root` / `.dark` blocks in `globals.css`. One config controls the whole library's
colors and radius, and every component picks it up because they already read `cx.theme()`:

```rust
use celestia_ui::theme::{hex, AppTheme, Scheme};
use gpui::px;

let config = AppTheme {
    radius: px(10.),
    light: Scheme {
        primary: Some(hex(0x2563eb)),
        ..Default::default()
    },
    dark: Scheme {
        primary: Some(hex(0x6aa5ff)),
        ..Default::default()
    },
};

// Re-themes the whole window on the next frame, and survives later
// Theme::change / system-appearance switches.
config.apply(cx);
```

The semantics mirror shadcn's variable layer:

- **Overlay, not replacement.** Every `Scheme` field is optional; `None` (the default) keeps the
  Celestia value from `theme.json`, so `AppTheme::default().apply(cx)` is a re-assert, not a
  change. Colors are written as `hex(0xrrggbb)` — the config's unit, like a CSS variable value.
- **One token drives every key it owns.** Setting `primary` re-colors the primary fills and their
  derived hover/active steps, `button.primary.*`, `ring`, `caret`, `link.*`, the slider/progress
  fills, `drag.border`, the list/table active borders, the 22% `selection` wash and the
  primary-tinted surfaces (`list/tab/table.active`, `drop_target`, at 10% over the background) —
  the same fan-out `theme.json` encodes by hand. The full shadcn set is covered, per mode:
  `background`, `foreground`, `surface` (the `#fafafa` chrome family — title bar, status bar, tab
  bar, group boxes, striped rows), `popover`, `primary`, `secondary`, `muted`, `accent`, the four
  status accents (`destructive`/`success`/`warning`/`info`, each with a foreground), `border`,
  `input`, `ring` and the `sidebar` family.
- **One radius.** `radius` maps to shadcn's `--radius`; the large-element radius (`radius_lg` —
  dialogs, notifications) derives as `radius + 4px`, the shadcn `--radius-xl` step.
- **Mode-safe.** `apply` overlays the active family and re-applies the current mode, so toggling
  light/dark (`Theme::change`, `sync_system_appearance`) keeps using the configured palettes.

### Multi-theme families

Light, dark and **custom themes** ride the same token vocabulary. A theme *family* is a named
light + dark pair; `install()` seeds the `Celestia` family from `theme.json` and
`crates/ui/src/theme/book.rs` keeps the registry of families plus the active one:

```rust
use celestia_ui::theme::{active, families, hex, select, AppTheme, Scheme};
use gpui::px;

// Register a custom family (named light+dark pair over the Celestia base)
// and activate it:
AppTheme {
    radius: px(8.),
    dark: Scheme {
        background: Some(hex(0x0b1120)),
        primary: Some(hex(0x38bdf8)),
        ..Default::default()
    },
    ..Default::default()
}
.register("Nocturne", cx);

select("Celestia", cx); // switch back — the mode (light/dark) is preserved
families(cx);           // ["Celestia", "Nocturne"]
active(cx);             // "Celestia"
```

The mechanics, all on top of `gpui-component`'s `Theme` / `ThemeColor` / `ActiveTheme` (re-exported at
`celestia_ui::theme` so apps reach the whole story in one place):

- **Families are semantic-token overlays, not style forks.** `register` derives the pair from the
  Celestia base with the same fan-out as `apply`, names the configs `"<Family> Light/Dark"` and
  activates them. Re-registering a name replaces that family.
- **`apply` is family-aware.** It overlays whichever family is active and stores the result on it,
  so token tweaks survive switching away and back.
- **The book, not the registry.** Families live in a private global because `gpui-component`'s
  `ThemeRegistry` has no public replace; its change observer skips names it does not know, so
  custom themes are untouched by registry churn.
- **Mode toggles stay inside the family.** `Theme::change` / system-appearance sync keep operating
  on the active pair; ⌘D in the showcase flips light/dark within it.

Pinned behavior lives in the `config.rs` tests (default apply is a no-op, the radius derivation,
per-mode primary/destructive overrides and their fan-out) and the `book.rs` tests (register /
select / apply interplay). The showcase's **Theming & Config** section
(`crates/showcase/src/sections/theming.rs`) switches families, registers a `Nocturne` custom
theme, and swaps radius presets and accent palettes live.

The mode-independent colors (`brand`, `brand_deep`, `brand_foreground`, the chart ramp) stay in
`palette.rs` — like the web `:root`, they are defined once and never re-themed.

## State management

`crates/ui/src/state/` is the desktop counterpart of the web app's zustand stores and React
contexts, built on GPUI's entity model (an entity re-renders when it calls `cx.notify()`). Two
layers:

- **`Store` / `StoreHandle`** — the zustand layer. `StoreHandle::new(state, cx)` creates a store
  entity; `read(cx)` is `getState()`, `set(cx, …)` / `update(cx, …)` are `setState()` and notify
  every observer, `replace(cx, state)` swaps the whole value, and `set_if_changed` skips the
  notification when the state compares equal afterwards. Actions are plain `&mut self` methods on
  the state type, passed as the closure: `store.set(cx, AppState::close_tab)`.
- **`StoreContext<T>`** — the React-context layer. `StoreContext::<T>::provide(state, cx)` registers
  an ambient, store-backed value once at bootstrap; any code later calls
  `StoreContext::<T>::require(cx)` (or `consume`) and gets the full read/write handle with no prop
  drilling. There is one ambient value per state type per app — for multiple live instances of the
  same type, skip the ambient layer and hand out `StoreHandle`s explicitly.

The re-render gate is `observe_slice`: bind an entity to a selector over the state, and its callback
(where you call `cx.notify()`) only runs when that slice's value actually changes — the
`useStore(selector)` equivalent. `subscribe` is the unfiltered variant for side effects
(persistence, logging). Like GPUI's own observers, callbacks run once per update batch with that
batch's final state, not once per `set` call.

The showcase's **State & Stores** section (`crates/showcase/src/sections/state.rs`) renders this
live: a `GalleryState` store with per-slice notification counters, and a `Session` ambient context
provided in `main.rs`. The layer is unit-tested with `#[gpui::test]` tests inside
`crates/ui/src/state/`.

Full usage guide — defining stores, actions, gating, contexts, testing, and the live demo — at
[Desktop State](/docs/desktop-state).

## Building a desktop app on it

Depend on the crate (`celestia-ui = { path = "…/crates/ui" }`, plus `gpui`,
`gpui-base`, `gpui-component` and `gpui-platform`), register
the asset source with `.with_assets(celestia_ui::assets::CelestiaAssets)` (see
[Icons — Phosphor](#icons--phosphor) — without it icons render blank), call
`celestia_ui::init(cx)` inside `application().run(...)` before opening any window, and wrap
your root view in a `gpui-component` `Root`. Mount the Dialog/Sheet/Notification layers in your root
view's render (`Root::render_dialog_layer` / `render_sheet_layer` / `render_notification_layer`) —
`Root::render` does not draw them, and `WindowExt` (`open_dialog`, `open_sheet`,
`push_notification`) targets nothing until they are mounted. The showcase's
`crates/showcase/src/main.rs` is the full reference bootstrap: window options,
keybindings, stateful entities (`InputState`, `SelectState`), the mounted layers and
builder-style component usage across every primitive.
