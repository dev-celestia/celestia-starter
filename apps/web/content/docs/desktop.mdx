`celestia-ui` is the desktop counterpart of `@celestia-project/ui`: a Rust component library for
native desktop apps built on [GPUI](https://gpui.rs) through **gpui-kit 0.6** (which pins the
matching `gpui` and `gpui-component` versions — one dependency line locks the whole stack). The
shape mirrors the web package: `packages/ui` wraps Base UI primitives with celestia tokens;
`celestia-ui` wraps the gpui-component library the same way, so most web files map 1:1 onto a
desktop module (`drawer.tsx` → `sheet`, `toast.tsx` → `notification`, `file-tree.tsx` → `tree`).

</Callout>

<Callout type="warn" title="Invisible to pnpm and turbo">

  see it — run `cargo` directly inside `packages/desktop/`, or use the root
  `pnpm desktop` script, which shells into cargo. Nothing under this package
  participates in `turbo typecheck` or the web build.
</Callout>

## Running it

Rust **≥ 1.97** (edition 2024); no environment variables — the theme JSON is compile-time
embedded. macOS needs no extra toolchain, Linux needs Vulkan + Wayland/X11/fontconfig headers,
Windows needs MSVC.

```bash
pnpm desktop                        # from the repo root — build & open the gallery window
cargo run -p celestia-desktop       # or directly from packages/desktop/  (⌘D / Ctrl+D toggles theme)
cargo test --workspace              # unit + gpui TestAppContext tests (theme pins live here)
```

## Architecture

One file per primitive, mirroring `packages/ui/src/components/primitive/*.tsx`:

1. **Celestia wrappers** — components with a shadcn-shaped prop surface that
   render gpui-kit primitives under Celestia theming: `button.rs` (`Button` +
   `ButtonVariant` primary/secondary/destructive/outline/ghost/link +
   `ButtonSize`), `badge.rs` (`Badge` + `BadgeVariant`, including a `Brand`
   variant), `card.rs`, `section_heading.rs`, `text_editor.rs` and
   `code_editor.rs`.
2. **Per-primitive re-exports** — every other primitive gets its own file
   (`switch.rs`, `alert.rs`, `popover.rs`, `table.rs`, …) re-exporting the
   matching gpui-component API, with a doc comment recording the web-file →
   desktop mapping (the table below). Wrapper types are also flattened at
   `celestia_ui::components::*` (e.g. `components::Button`); module-only
   primitives are reached through their module path
   (`components::table::…`).

One rule runs through everything: **raw hex lives only in `theme.json` and `palette.rs`**. Call
sites take colors by role through `cx.theme()` (semantic roles: background, foreground, primary,
border, sidebar…) or `palette(cx)` (brand + charts).

## Zeron-port primitives

A first family of primitives is ported from the Zeron reference (`reference/zeron`, a GPUI chat
app). These are celestia-native APIs — colors resolve from `cx.theme()` / `palette(cx)`, never
from zeron's theme — and all motion runs through one shared module:

- `celestia_ui::motion` — the animation kit: CSS-exact `CubicBezier` curves, a `MotionSpec`
  catalog (`FADE_IN`, `MENU_IN`, `DIALOG_IN`, `PULSE`, `GRADIENT_SPIN`, …) with entrance helpers
  (`fade_in`, `menu_in`, `dialog_in`), premultiplied-sRGB `mix`, and the **pulse clock**: a shared
  ~30fps driver that keeps every mounted loader phase-locked and parks entirely once the last one
  unmounts (a window with no spinner schedules nothing). Reduced motion (gpui's
  `reduce_motion` flag) snaps loaders to a static rest brightness and zeroes the wave phases.
- `components/loaders.rs` — the cell loaders: `pulse_loader` (5-cell opacity/scale wave),
  `gradient_spinner` (3×3 grid on the `brand → brand_deep` ramp, the pulse travels
  bottom-edge → top-centre), `mini_spinner` / `mini_mono_spinner` (2×3 radial chase in a
  self-contained view), and `progress_ring` (stroked-polyline radial percent, works over dimmed
  imagery with a white tint).
- `components/notice.rs` — `notice_chip`: the tinted failure card (accent wash + border, alert
  triangle, copy-to-clipboard button, wrapping message — never truncating stderr), `Plain`
  (inline) and `Tile` (block) icon treatments, danger/warning palettes.
- `components/context_badge.rs` — `MessageBadge` pills with `BadgeDetail` rows: a 24px chip that
  lifts a hover card of location/tag/body rows after a 280ms hover delay. The three slots are
  generic — the module never learns what the context cites.

The gallery's **Feedback** section renders all of them live.

<Callout type="warn" title="What could not be ported from Zeron">
  Zeron does not run stock gpui — it builds on its fork `zeronsh/zui` (checked
  out at `reference/zui`), which adds renderer-level primitives: `BackdropBlur`
  (frosted glass), per-pixel `EdgeFade` / `Window::with_edge_fade` (scroll-edge
  fades), transparent-window compositing and image corner-radius masks.
  gpui-kit's pinned `gpui` (the `gpui-pre` series) has none of these, so zeron's
  `frost.rs`, `glass.rs` and `edge_fade.rs` stay unported — adopting them would
  mean replacing the whole gpui-kit-locked stack with the fork. Everything built
  on the shared core API (div/Styled, `Animation`, `canvas`, element state)
  ports cleanly, which is the family above.
</Callout>

## Icons — Phosphor

`crates/ui/src/components/icon.rs` ships the **Phosphor** icon set (Phosphor Core 2.1.1, MIT —
license vendored at `assets/phosphor/LICENSE-PHOSPHOR`). The upstream
[`gpui-phosphor`](https://docs.rs/gpui-phosphor) crate can't be used directly — it targets the
`gpui` 0.2 lineage and can't link against gpui-kit's `gpui-pre` types — so the approach is ported
onto this stack instead:

- **SVGs** — 1,512 glyphs × 3 weights (`regular`, `bold`, `fill`) vendored under
  `crates/ui/assets/phosphor/<weight>/<name>.svg`. Duotone is skipped: GPUI's SVG renderer paints
  every path with one color, so duotone would render as solid.
- **`PhosphorIcon`** — a typed catalog enum generated by `crates/ui/build.rs` at compile time
  (`PhosphorIcon::Heart`, `PhosphorIcon::PaperPlaneTilt`, …, plus `ALL` / `COUNT` / `name()`).
  It implements gpui-kit's `IconNamed`, so it plugs straight into gpui-kit's `Icon` at the
  regular weight — `Icon::new(PhosphorIcon::Heart)` — and bare `.child(PhosphorIcon::Heart)`
  renders at the surrounding text style.
- **`Phosphor`** — the weight-aware wrapper (the counterpart of gpui-phosphor's `Icon` builder):
  `Phosphor::new(PhosphorIcon::Heart).weight(PhosphorWeight::Fill).size(px(20.)).color(…)`.
  Size and color default to the surrounding text style. The weight is just the asset-path prefix
  (`phosphor/<weight>/<name>.svg`), so every enum variant exists at every embedded weight.

```bash
cargo test --workspace   # asset-source tests: every glyph resolves at every weight
```

### Asset source registration (required)

gpui takes a **single asset source at startup**. Register the composite from
`celestia_ui::assets` in `main` — Phosphor paths resolve first, gpui-kit's default Lucide bundle
falls through second:

```rust
use celestia_ui::assets::CelestiaAssets;

gpui_kit::platform::application()
    .with_assets(CelestiaAssets)          // phosphor/… + icons/…
    .run(|cx| { /* … */ });
```

Without a registered source gpui's fallback serves nothing and **every icon renders blank
silently** — the showcase previously hit exactly that for its Lucide icons, and
`CelestiaAssets` fixes it. The gallery's **Phosphor Icons** section
(`crates/showcase/src/sections/icons.rs`) renders the full catalog with live search, a
Regular/Bold/Fill weight switcher, and click-to-copy `PhosphorIcon::…` names.

## Theming

`crates/ui/src/theme.json` is the sRGB-hex port of
`packages/ui/src/styles/globals.css` — the web CSS file stays the single source of truth, and the
JSON is re-derived from it when tokens change (grays via OKLab → linear sRGB = L³, chromatic
tokens through full OKLab → sRGB with gamut clamping, alpha tokens as 8-digit hex). `init()` loads
the JSON into the `ThemeRegistry` and **replaces** gpui-kit's default light/dark configs, so
`Theme::change` and system-appearance sync keep using the Celestia palettes with no re-patching.

Key values are pinned by `cargo test --workspace`: light `primary` `#d40c1a`, dark `#ff4d46`
(out-of-gamut `oklch(0.68 0.22 27)` clipped), the dark border as white-alpha, `selection` always
primary at 22%, and a guard test that fails if primary ever regresses to the retired brand blue.
Beyond the semantic roles, `palette(cx)` carries the mode-independent product colors — `brand`
`#dc2626`, `brand_deep` `#b51230`, `brand_foreground` and the grayscale chart ramp — mirroring the
web where these live once on `:root`.

### Global theme config

`theme.json` is the compiled-in default; the runtime knob over it is
**`celestia_ui::theme::AppTheme`** (`crates/ui/src/theme/config.rs`) — the desktop counterpart of
the shadcn `:root` / `.dark` blocks in `globals.css`. One config controls the whole library's
colors and radius, and every component picks it up because they already read `cx.theme()`:

```rust
use celestia_ui::theme::{hex, AppTheme, Scheme};
use gpui_kit::px;

let config = AppTheme {
    radius: px(10.),
    light: Scheme {
        primary: Some(hex(0x2563eb)),
        ..Default::default()
    },
    dark: Scheme {
        primary: Some(hex(0x6aa5ff)),
        ..Default::default()
    },
};

// Re-themes the whole window on the next frame, and survives later
// Theme::change / system-appearance switches.
config.apply(cx);
```

The semantics mirror shadcn's variable layer:

- **Overlay, not replacement.** Every `Scheme` field is optional; `None` (the default) keeps the
  Celestia value from `theme.json`, so `AppTheme::default().apply(cx)` is a re-assert, not a
  change. Colors are written as `hex(0xrrggbb)` — the config's unit, like a CSS variable value.
- **One token drives every key it owns.** Setting `primary` re-colors the primary fills and their
  derived hover/active steps, `button.primary.*`, `ring`, `caret`, `link.*`, the slider/progress
  fills, `drag.border`, the list/table active borders, the 22% `selection` wash and the
  primary-tinted surfaces (`list/tab/table.active`, `drop_target`, at 10% over the background) —
  the same fan-out `theme.json` encodes by hand. The full shadcn set is covered, per mode:
  `background`, `foreground`, `surface` (the `#fafafa` chrome family — title bar, status bar, tab
  bar, group boxes, striped rows), `popover`, `primary`, `secondary`, `muted`, `accent`, the four
  status accents (`destructive`/`success`/`warning`/`info`, each with a foreground), `border`,
  `input`, `ring` and the `sidebar` family.
- **One radius.** `radius` maps to shadcn's `--radius`; the large-element radius (`radius_lg` —
  dialogs, notifications) derives as `radius + 4px`, the shadcn `--radius-xl` step.
- **Mode-safe.** `apply` overlays the active family and re-applies the current mode, so toggling
  light/dark (`Theme::change`, `sync_system_appearance`) keeps using the configured palettes.

### Multi-theme families

Light, dark and **custom themes** ride the same token vocabulary. A theme *family* is a named
light + dark pair; `install()` seeds the `Celestia` family from `theme.json` and
`crates/ui/src/theme/book.rs` keeps the registry of families plus the active one:

```rust
use celestia_ui::theme::{active, families, hex, select, AppTheme, Scheme};
use gpui_kit::px;

// Register a custom family (named light+dark pair over the Celestia base)
// and activate it:
AppTheme {
    radius: px(8.),
    dark: Scheme {
        background: Some(hex(0x0b1120)),
        primary: Some(hex(0x38bdf8)),
        ..Default::default()
    },
    ..Default::default()
}
.register("Nocturne", cx);

select("Celestia", cx); // switch back — the mode (light/dark) is preserved
families(cx);           // ["Celestia", "Nocturne"]
active(cx);             // "Celestia"
```

The mechanics, all on top of gpui-kit's `Theme` / `ThemeColor` / `ActiveTheme` (re-exported at
`celestia_ui::theme` so apps reach the whole story in one place):

- **Families are semantic-token overlays, not style forks.** `register` derives the pair from the
  Celestia base with the same fan-out as `apply`, names the configs `"<Family> Light/Dark"` and
  activates them. Re-registering a name replaces that family.
- **`apply` is family-aware.** It overlays whichever family is active and stores the result on it,
  so token tweaks survive switching away and back.
- **The book, not the registry.** Families live in a private global because gpui-kit's
  `ThemeRegistry` has no public replace; its change observer skips names it does not know, so
  custom themes are untouched by registry churn.
- **Mode toggles stay inside the family.** `Theme::change` / system-appearance sync keep operating
  on the active pair; ⌘D in the showcase flips light/dark within it.

Pinned behavior lives in the `config.rs` tests (default apply is a no-op, the radius derivation,
per-mode primary/destructive overrides and their fan-out) and the `book.rs` tests (register /
select / apply interplay). The showcase's **Theming & Config** section
(`crates/showcase/src/sections/theming.rs`) switches families, registers a `Nocturne` custom
theme, and swaps radius presets and accent palettes live.

The mode-independent colors (`brand`, `brand_deep`, `brand_foreground`, the chart ramp) stay in
`palette.rs` — like the web `:root`, they are defined once and never re-themed.

## State management

`crates/ui/src/state/` is the desktop counterpart of the web app's zustand stores and React
contexts, built on GPUI's entity model (an entity re-renders when it calls `cx.notify()`). Two
layers:

- **`Store` / `StoreHandle`** — the zustand layer. `StoreHandle::new(state, cx)` creates a store
  entity; `read(cx)` is `getState()`, `set(cx, …)` / `update(cx, …)` are `setState()` and notify
  every observer, `replace(cx, state)` swaps the whole value, and `set_if_changed` skips the
  notification when the state compares equal afterwards. Actions are plain `&mut self` methods on
  the state type, passed as the closure: `store.set(cx, AppState::close_tab)`.
- **`StoreContext<T>`** — the React-context layer. `StoreContext::<T>::provide(state, cx)` registers
  an ambient, store-backed value once at bootstrap; any code later calls
  `StoreContext::<T>::require(cx)` (or `consume`) and gets the full read/write handle with no prop
  drilling. There is one ambient value per state type per app — for multiple live instances of the
  same type, skip the ambient layer and hand out `StoreHandle`s explicitly.

The re-render gate is `observe_slice`: bind an entity to a selector over the state, and its callback
(where you call `cx.notify()`) only runs when that slice's value actually changes — the
`useStore(selector)` equivalent. `subscribe` is the unfiltered variant for side effects
(persistence, logging). Like GPUI's own observers, callbacks run once per update batch with that
batch's final state, not once per `set` call.

The showcase's **State & Stores** section (`crates/showcase/src/sections/state.rs`) renders this
live: a `GalleryState` store with per-slice notification counters, and a `Session` ambient context
provided in `main.rs`. The layer is unit-tested with `#[gpui_kit::test]` tests inside
`crates/ui/src/state/`.

Full usage guide — defining stores, actions, gating, contexts, testing, and the live demo — at
[Desktop State](/docs/desktop-state).

## Building a desktop app on it

Depend on the crate (`celestia-ui = { path = "…/crates/ui" }` + `gpui-kit = "0.6.1"`), register
the asset source with `.with_assets(celestia_ui::assets::CelestiaAssets)` (see
[Icons — Phosphor](#icons--phosphor) — without it icons render blank), call
`celestia_ui::init(cx)` inside `application().run(...)` before opening any window, and wrap
your root view in a gpui-kit `Root`. Mount the Dialog/Sheet/Notification layers in your root
view's render (`Root::render_dialog_layer` / `render_sheet_layer` / `render_notification_layer`) —
`Root::render` does not draw them, and `WindowExt` (`open_dialog`, `open_sheet`,
`push_notification`) targets nothing until they are mounted. The showcase's
`crates/showcase/src/main.rs` is the full reference bootstrap: window options,
keybindings, stateful entities (`InputState`, `SelectState`), the mounted layers and
builder-style component usage across every primitive.
