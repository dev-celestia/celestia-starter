`@celestia-project/mobile` is the native counterpart to `@celestia-project/ui`: a component
library for Expo apps with **157 modules**. A small set of components hosts **real platform
views** — SwiftUI on iOS, Jetpack Compose on Android — through `@expo/ui`; the rest are drawn
in React Native and animated through a centralized `motion` module — named spring presets over
core `Animated` (the house spring `SPRING` is damping 18 / mass 1 / stiffness 320) plus
procedural loops for spinners, pulses and indeterminate progress. `MobileSwitch` is now
**drawn and animated** rather than a hosted `@expo/ui` control.

<Callout type="info" title="Looking for the visual tour?">
This page is the technical reference — install, peer dependencies, platform support, API.
For the token ramp and a gallery of the screens, see the dedicated
**[Mobile showcase](/mobile)** surface.
</Callout>

It is not a port of the web library. The web components assume a DOM, hover states and a CSS
box model; the mobile components assume a thumb, a safe area and a touch target floor. What the
two packages share is the **taxonomy** (the same `primitive` / `composite` / `ai` / `layout` split) and
the **design tokens**, so a component sits in the same mental bucket whichever library you are in.

<Callout type="info" title="Routing- and data-agnostic by contract">
Every component here is presentational: props in, callbacks out. There is no navigation library,
no data fetching, and no auth client. The host app owns routing, data and session state — which is
why this package has no dependency on `apps/api` and can be dropped into any Expo project.
</Callout>

## Running the showcase

`pnpm mobile` starts the Metro dev server for `apps/mobile`. The root script is
`turbo dev --filter=mobile`, which resolves to the package's `dev` script (`expo start`); Turbo
auto-detects the `expo` framework and `turbo.json` marks `dev` persistent and uncached, so it stays
attached like any other dev server. Metro itself is platform-agnostic — you pick a target after it
boots, or ask for one up front:

| Command | Target | Status |
|---------|--------|--------|
| `pnpm mobile` | Metro only — press `i`, `a` or `w` in the terminal | — |
| `pnpm --filter mobile ios` | iOS simulator or device (`expo start --ios`) | Supported |
| `pnpm --filter mobile android` | Android emulator or device (`expo start --android`) | Supported |
| `pnpm --filter mobile web` | Browser (`expo start --web`) | Supported — see [Platform support](#platform-support) |

Each target needs its own toolchain: Xcode and a booted simulator for iOS, the Android SDK and a
running emulator for Android. Web needs nothing beyond the three packages listed under
[Enabling web](#enabling-web).

`@expo/ui` is **included in Expo Go**, so the real SwiftUI and Compose views run in the sandbox
client with no native build at all — scan the QR code from `pnpm mobile` and the showcase opens on
a physical device. A development build (`npx expo run:ios` / `npx expo run:android`) is only
needed once you add native code of your own.

```bash
# Typecheck just the library
pnpm --filter @celestia-project/mobile typecheck
```

## Platform support

The library targets **iOS, Android and web**. The native platforms get real SwiftUI and Jetpack
Compose views through `@expo/ui`; web is served by `@expo/ui`'s **universal** entry, which is what
every component in this package imports.

| | iOS | Android | Web |
|---|-----|---------|-----|
| Hosted `@expo/ui` components (`MobileHost`, `MobileList`, `MobileBottomSheet`) | ✅ SwiftUI | ✅ Compose | ✅ DOM equivalents |
| Rest of the package (plain React Native) | ✅ | ✅ | ✅ via `react-native-web` |
| Skia-drawn components (`MobileSparkline`, `MobileChartBar` / `-Line` / `-Pie` / `-Scatter`, `MobileProgressRing`) | ✅ native Skia | ✅ native Skia | ✅ CanvasKit WASM — needs the bootstrap under [Enabling web](#enabling-web) |
| `apps/mobile` showcase | ✅ | ✅ | ✅ |

`@expo/ui@57` exposes three entry points, and *which one you import* decides whether web works:

| Import | Implementation |
|--------|----------------|
| `@expo/ui` | **Universal** — resolves to `.ios.tsx` / `.android.tsx` / a generic DOM implementation |
| `@expo/ui/swift-ui` | iOS only |
| `@expo/ui/jetpack-compose` | Android only |

The modules that host native views — `MobileHost`, `MobileList` and `MobileBottomSheet` —
import from `"@expo/ui"` (the universal entry), never from `/swift-ui` or `/jetpack-compose`.
The universal implementations are real rather than stubs: `Host` renders a plain `View`, `List`
and `ListItem` use plain React Native primitives, and `BottomSheet` renders through
[`vaul`](https://vaul.emilkowal.ski/). Everything else in the package is plain React Native and
needs no `@expo/ui` at runtime.

The rest of the chain is web-clean as well. `react-native-safe-area-context` resolves through
`react-native-web`; `expo-haptics` — which every interactive component calls — ships a no-op
`ExpoHaptics.web.ts`, so haptics simply do nothing in a browser; `expo-status-bar` ships
`StatusBar.web.js`; and `react-native-svg`, which the showcase icons are drawn with, ships a web
build. Every animation takes its driver guard from `canUseNativeDriver` in `src/motion.ts`, and `screen.tsx` puts the
iOS-only `padding` keyboard behind a `Platform.OS === "ios"` check.

### Enabling web

`apps/mobile` needs three packages for the browser target; `expo install` picks the SDK-compatible
versions:

```bash
npx expo install react-native-web react-dom @expo/metro-runtime
```

and `app.json` has to declare the web bundler:

```json
"web": { "bundler": "metro", "output": "single" }
```

Both are already in place, so `pnpm --filter mobile web` serves the showcase in a browser.

### The Skia runtime

Everything else in the package is plain React Native, but six components are drawn with Skia:
`MobileSparkline`, `MobileChartBar`, `MobileChartLine`, `MobileChartPie`, `MobileChartScatter` and
`MobileProgressRing`. On iOS and Android Skia is a native module that ships with the app. In the
browser it is **CanvasKit** — a WebAssembly build of Skia that has to be fetched and instantiated
before anything drawn with Skia can render.

#### Defer the import, not the render

This is the part that is easy to get wrong. `Skia` is not a lazy getter, it is a module-level
constant:

```js
// @shopify/react-native-skia/lib/module/skia/Skia.web.js
export const Skia = JsiSkApi(global.CanvasKit)
```

Whatever `global.CanvasKit` holds the moment that module is first evaluated is what `Skia` stays
forever. So importing the app before CanvasKit is ready does not give you a slow first chart — it
gives you `Cannot read properties of undefined (reading 'PathBuilder')` the first time a Skia
component mounts, which unmounts the entire tree and leaves a blank page. Waiting at render time
cannot help, because by then the module has already been evaluated. **The `import` itself has to be
deferred**, which is why `apps/mobile` splits its entry point in two:

| File | Target | Job |
|------|--------|-----|
| `index.ts` | both | `registerRootComponent(Root)` — and nothing else |
| `src/Root.tsx` | native | re-exports `./App`; Skia is already installed |
| `src/Root.web.tsx` | web | loads CanvasKit, then `await import("./App")` |

```tsx
// apps/mobile/src/Root.web.tsx (abridged)
export function Root() {
  const [app, setApp] = React.useState<React.ComponentType | null>(null)

  React.useEffect(() => {
    void (async () => {
      await LoadSkiaWeb({ locateFile: () => canvaskitWasm })
      const { default: App } = await import("./App")
      setApp(() => App)
    })()
  }, [])

  return app === null ? <LoadingScreen /> : <App />
}
```

Metro picks `Root.web.tsx` over `Root.tsx` by platform extension, so `App.tsx` itself stays
Skia-agnostic — it is the same five-provider tree on every target.

Two consequences worth knowing:

- **The loading screen may only use Skia-free imports.** It renders with the real theme, so it uses
  `@celestia-project/mobile/host` and `.../primitive/spinner` — the deep entry points — rather than
  the root barrel, which also re-exports the chart components. Same reason `.../composite/alert` is
  imported directly for the failure state.
- **The dynamic import is what splits the bundle.** `expo export` emits an initial chunk
  (`index-*.js`, ~860 KB: React Native Web, the theme layer and the CanvasKit glue) plus an async
  chunk (`App-*.js`, ~2.5 MB: the gallery and Skia). Nothing Skia-shaped is in the initial chunk, so
  the loading screen paints without it.

The wasm is imported as a **Metro asset**, so `metro.config.js` has to register the extension:

```js
config.resolver.assetExts.push("wasm")
```

Metro then emits the binary into the bundle's asset folder and the import resolves to its URL, which
is what `locateFile` hands back. This behaves identically under `expo start` and `expo export`. The
alternative in Skia's own docs is `npx setup-skia-web`, which copies the binary into `public/` and
lets emscripten's default `locateFile` find it next to `index.html` — that needs a build step and a
7 MB file in the repository, so the asset import is preferred here.

Two things to know:

- **Props marked `@platform ios` / `@platform android` are inert on web.** `MobileList`'s
  `onRefresh` is the one in this package: the prop is accepted and ignored, because there is no
  native refresh affordance to show.
- **Web is a preview surface, not a port.** The DOM rendering comes from `@expo/ui` and
  `react-native-web`, so it is close to, but not pixel-identical with, the SwiftUI / Compose
  rendering. When a feature needs a first-class web implementation, use `@celestia-project/ui`;
  the two libraries share design tokens and the primitive / composite / ai / layout taxonomy precisely
  so that the same screen can have a native and a browser implementation.

## Installation

Inside a workspace app the package resolves from the workspace protocol:

```bash
pnpm --filter mobile add @celestia-project/mobile@workspace:*
```

The native dependencies are peer dependencies and must be installed by the app, because they
contain platform code that Expo has to autolink:

```bash
npx expo install @expo/ui expo-haptics react-native-safe-area-context
```

Pin `react-native` to the version Expo SDK 57 pairs with (`0.86.3`) — `npx expo install
react-native` resolves it. Do not bump to `^0.87` manually: Expo 57's Metro tooling requires
`rn-get-polyfills`, which React Native 0.87 removed.

## Component categories

Components are grouped by **role**, not by atomicity — the same rule `@celestia-project/ui` uses,
so the two libraries read the same way.

| Category | Directory | What belongs here | Rule of thumb |
|----------|-----------|-------------------|---------------|
| **primitive** | `src/components/primitive/` | Generic building blocks. Each wraps one native control or one plain surface. | *"Would I reach for this in any app?"* |
| **composite** | `src/components/composite/` | Opinionated assemblies built from primitives. | *"Is this a `<Primitive>` with a specific job?"* |
| **ai** | `src/components/ai/` | Assistant, agent and generative surfaces — transcript, composer, model and context controls, grounding and feedback. | *"Does it only make sense next to a model?"* |
| **layout** | `src/components/layout/` | Full-screen shells and screens. Own the frame; take content through slots. | *"Does it own the whole screen?"* |

<Callout type="note" title="“Primitive” means generic, not atomic">
`MobileCard` ships `MobileCardHeader`, `MobileCardTitle`, `MobileCardDescription`,
`MobileCardContent` and `MobileCardFooter` — and is still a primitive, exactly as `Card` is in
`@celestia-project/ui/primitive`. A compound component is not automatically a composite; only an
*opinionated* one is.
</Callout>

## Setup

`MobileHost` bridges React Native to the native layer and provides the theme context every
component reads.

<Callout type="warn" title="MobileHost must be given a size">
`MobileHost` renders `@expo/ui`'s `Host`, whose `matchContents` and `useViewportSizeMeasurement`
props both default to `false`. An **unsized host lays out to zero height**, so every child
collapses with it and the app renders as a blank screen — the root view's background, and nothing
else. `style={{ flex: 1 }}` is the fix, and it is not optional.

Reach for `useViewportSizeMeasurement` instead when the host should size to the available viewport,
or `matchContents` when it should shrink to fit its content.
</Callout>

`SafeAreaProvider` must sit above it so `MobileScreen` can resolve insets, and
`MobileToastProvider` must sit inside a **sized** parent, because its overlay positions itself
absolutely against that parent.

```tsx
import * as React from "react"
import { View } from "react-native"
import { SafeAreaProvider } from "react-native-safe-area-context"
import { MobileHost, MobileToastProvider } from "@celestia-project/mobile"

export default function App() {
  return (
    <SafeAreaProvider>
      <MobileHost style={{ flex: 1 }}>
        <View style={{ flex: 1 }}>
          <MobileToastProvider>{/* your navigator / screens */}</MobileToastProvider>
        </View>
      </MobileHost>
    </SafeAreaProvider>
  )
}
```

Pass `forcedTheme="light" | "dark"` to `MobileHost` to override the device preference — the
showcase uses this for its theme toggle.

## Motion

All spring physics lives in one module, `src/motion.ts`. Before it existed, every component
carried its own hand-tuned `damping`/`stiffness` pair — nine distinct dampings and eleven
distinct stiffnesses across the library, with the house spring retyped in full in a dozen
files. Components now import a name that describes the *intent* of the motion, so the feel of
the whole system is tunable in one place:

| Preset | Values | Intent |
|--------|--------|--------|
| `SPRING` | 18 / 1 / 320 | The house spring — state changes: selection, toggles, indicator travel |
| `SPRING_SOFT` | 22 / 1 / 260 | Layout reveals (height, collapse) where a tight spring reads as a jump-cut |
| `SPRING_SNAPPY` | 14 / 1 / 380 | Confirmation pops — the check tick, the radio dot, the badge pop — where the overshoot IS the feedback |
| `SPRING_ENTRANCE` | 16 / 1 / 240 | Arrivals: content enters with a small overshoot and a little energy |
| `SPRING_EXIT` | 22 / 1 / 320 | Dismissals: overdamped and decisive — nothing re-enters the frame to apologize |
| `SPRING_GAUGE` | 20 / 1 / 120 | Gauges and progress fills, where overshoot would misreport the value |

Three helpers attach the native-driver guard every call site used to repeat
(`canUseNativeDriver` is `false` on web, so a browser build degrades to the JS driver instead
of throwing):

- `springTo(value, toValue, config?)` — one-line `Animated.spring` with a preset.
- `springLayoutTo(value, toValue, config?)` — the same for layout props (width, height), which
  cannot ride the native driver and are forced onto the JS driver.
- `pressInTiming(value, toValue, duration?)` — the 90 ms press-in dip. Press-in is deliberately
  **not** a spring: the finger is already down, and an overshoot under a held press reads as a
  wobble. A fixed timing gets the surface to its pressed position before the release spring
  ever starts.

Two hooks cover the patterns nearly every interactive component used to re-roll.
`useSpringValue(target, config?)` is the declarative chase — an `Animated.Value` seeded at
`target` (so the first render never springs from zero) that springs after every subsequent
change. `usePressSpring(rest, pressed, config?)` returns a `value` plus `onPressIn`/`onPressOut`
handlers to spread on a `Pressable`; the pair drives whichever property the press should move —
buttons and FABs translate 0 → 2 over their hard edge, chips scale 1 → 0.96:

```tsx
import * as React from "react"
import { Animated, Pressable } from "react-native"
import { usePressSpring } from "@celestia-project/mobile"

export function Tile({ onPress }: { onPress?: () => void }) {
  // Press feedback in one line: dip to 0.96 on a 90ms timing in,
  // spring back to 1 on the house spring out.
  const { value: pressAnim, onPressIn, onPressOut } = usePressSpring(1, 0.96)

  return (
    <Animated.View style={{ transform: [{ scale: pressAnim }] }}>
      <Pressable onPress={onPress} onPressIn={onPressIn} onPressOut={onPressOut}>
        {/* ... */}
      </Pressable>
    </Animated.View>
  )
}
```

Two conventions keep the module honest:

- **Components never hand-type a `damping`/`mass`/`stiffness` tuple.** If no preset matches the
  intent, the preset list is wrong — extend `motion.ts`, not the call site.
- **Raw `Animated.timing` is reserved for intentional durations**: skeleton and status-dot
  pulses, the indeterminate progress loop, image load fades, the error shake. Those are timed
  effects, not springs, and stay written as such.

## Screens

The `layout` category is where this package diverges most from the web one. A screen owns the
whole frame — safe area, scrolling, keyboard avoidance, header, pinned footer — and takes its
content through slots.

### The shell + thin-screen split

`MobileScreen` is the base frame; its body is inset by a default 16pt gutter (the same one the
pinned footer uses), which `contentContainerStyle` merges over — pass `paddingHorizontal: 0`
for edge-to-edge content. `MobileAuthShell` adds the logo / heading / form / aside /
footer arrangement that all five auth screens share. Each auth screen then supplies **only** its
own fields and defaults:

```tsx
import { MobileSignInScreen } from "@celestia-project/mobile"

export default function SignIn() {
  const [error, setError] = React.useState<string>()
  const [loading, setLoading] = React.useState(false)

  return (
    <MobileSignInScreen
      error={error}
      loading={loading}
      socialProviders={[
        { id: "google", label: "Google" },
        { id: "apple", label: "Apple" },
      ]}
      onForgotPassword={() => router.push("/forgot-password")}
      onSignUp={() => router.push("/sign-up")}
      onSubmit={async ({ email, password }) => {
        setLoading(true)
        setError(undefined)
        try {
          await auth.signIn(email, password)
          router.replace("/")
        } catch (cause) {
          setError(cause instanceof Error ? cause.message : "Sign-in failed.")
        } finally {
          setLoading(false)
        }
      }}
    />
  )
}
```

The screen owns its **field** state and reports the result; it never authenticates, stores a
session or navigates. Server errors arrive back through `error`, which is why the same screen
works for a credential rejection, a network failure and an offline queue.

### Building a new screen

A new screen that resembles an existing one **composes the shell** — it never re-implements the
header. That is what stops six auth screens from drifting apart:

```tsx
import * as React from "react"
import { MobileAuthShell, MobileButton, MobileFormField, MobileTextInput } from "@celestia-project/mobile"

export function ChangeHandleScreen({ onSave }: { onSave: (handle: string) => void }) {
  const [handle, setHandle] = React.useState("")

  return (
    <MobileAuthShell
      heading="Choose a handle"
      subheading="This is how others will find you."
      onBack={() => history.back()}
    >
      <MobileFormField label="Handle" required>
        <MobileTextInput
          value={handle}
          onChangeText={setHandle}
          autoCapitalize="none"
          autoCorrect={false}
        />
      </MobileFormField>

      <MobileButton onPress={() => onSave(handle)}>Save</MobileButton>
    </MobileAuthShell>
  )
}
```

For a screen with no auth framing, compose `MobileScreen` directly and drive the header through
props — it renders a `MobileNavBar` as soon as you pass `title`, `onBack` or either header slot:

```tsx
<MobileScreen title="Reports" onBack={goBack} largeTitle>
  {/* content */}
</MobileScreen>
```

<Callout type="tip" title="Onboarding and settings">
`MobileOnboardingScreen` takes a `slides` array and handles paging, the page indicator and the
skip / next / get-started actions. `MobileSettingsScreen` takes `MobileSettingsSection` groups and
inserts the row separators for you — so a stray divider after the last row is impossible.
</Callout>

## Design rules

Every component in this package follows the same non-negotiables. Rules 1–6 are **measured** —
`pnpm audit:ui` runs `scripts/ui-audit/mobile-contrast.mjs`, which reads the ramp out of `tokens.ts`
and fails the build on a regression. The rest are held by convention and review. All of them are
worth knowing before adding a component:

1. **No hardcoded colours.** Everything reads `useMobileTheme()`; the light and dark ramps are both complete. `tokens.ts` is the only file in the package where a hex literal belongs — a `shadowColor` and a scrim both count, and both are tokens now.
2. **Status hues have a luminance ceiling of `L_rel <= 0.18333`.** Each of the four status hues is both a *fill* carrying white ink (`MobileBadge`, `MobileTag`, `MobileButton`) and *ink* on a near-white backdrop (`MobileAlert` title, form errors, `MobileProgress` fill). Both roles reduce to the same inequality — `1.05 / (L + 0.05) >= 4.5` — so one value per hue serves both and no token family needs splitting. **Do not lighten a status hue past the ceiling.** The ramp that did failed 19 WCAG AA pairings in light mode while dark passed every one; `pnpm audit:ui` now asserts all 38.
3. **Derived tokens must be re-derived.** `destructiveEdge` is the sRGB bake of the web token layer's `--shadow-destructive-3d` (`color-mix(in oklch, destructive, black 30%)`). Change `destructive` and the button's 2px bottom edge has to move with it, or the edge stops reading as a thickened border. The gate asserts the relationship numerically rather than trusting two literals that happen to agree.
4. **An escalating gauge needs a perceptible step.** `MobileTokenMeter` walks `muted` → `warning` → `destructive` on a 4pt bar, so adjacent steps must differ in contrast *or* hue. The luminance ceiling in rule 2 pins both status hues to the same lightness, which is why `destructive` sits a full ramp step below `warning`.
5. **Spacing comes from `spacing`.** Five steps — `inline` 4, `label` 8, `row` 12, `block` 16, `section` 32 — exported from `tokens.ts`, and re-exported by the showcase's `showcase/spacing.ts` so sections keep one import. The component layer predates the export and still carries off-scale literals; `pnpm audit:ui` prints the census each run so the remaining debt stays visible.
6. **44×44pt minimum touch target** on every interactive element (`metrics.minTouchTarget`). A control drawn shorter to match the web design system — `MobileButton` is 32px, `MobileSegmentedControl`'s segments are 36px — meets the floor with `hitSlop` (`hitSlopFor()` in `src/utils.ts` computes it) rather than by inflating the box. Vertical only: horizontal slop bleeds into the adjacent sibling, and React Native resolves the overlap in favour of the last-drawn one.
7. **Haptics fire on the causal commit frame** — `hapticLight()` for normal presses, `hapticMedium()` for destructive, `hapticSelect()` for toggles (all in `src/utils.ts`). Never on mount.
8. **16px font floor** on text inputs, to prevent OS viewport zoom.
9. **Tabular numerals** for counters, prices and timers.
10. **Icons arrive as props.** The package takes no icon dependency; only structural marks (a tick, a chevron, a magnifier) may be drawn inline. The showcase app is the consumer side of that rule and supplies its own set — see [Icons in the showcase](#icons-in-the-showcase).
11. **No hover-only affordances.**
12. **Forms never disable the submit button for empty fields.** It stays pressable and names what is missing; it is disabled only while loading.
13. **Screens are presentational.** Props in, callbacks out — no fetching, no auth client, no routing.
14. **Text children are wrapped; composed children are not.** `MobileButton`, `MobileBadge`, `MobileLink`, `MobileCardTitle` and `MobileCardDescription` route their children through `isTextChildren()` (`src/utils.ts`) to decide whether to wrap them in `MobileText`. Never replace it with `typeof children === "string"` or `React.isValidElement(children)`: JSX turns any element with more than one child into an **array** (`+{count}%` becomes `["+", count, "%"]`), and both of those checks mis-classify that array — the first renders bare strings outside a `<Text>` and the second nests a `<View>` inside one. Either way the app crashes at render.
15. **Animation goes through `src/motion.ts`.** Import the preset whose *intent* matches (`SPRING`, `SPRING_SNAPPY`, `SPRING_ENTRANCE`, …) or the `springTo` / `pressInTiming` / `usePressSpring` helpers — never a hand-typed `damping`/`stiffness` tuple. Raw `Animated.timing` is only for intentional durations (pulses, shakes, fades).

## Dependencies

The package adds **no runtime dependencies of its own** — with one declared exception. Two deliberate consequences:

- **Paging** uses `ScrollView` + `pagingEnabled`, not `reanimated` or `gesture-handler`.
- **Motion** uses React Native's built-in `Animated` behind the centralized `motion` module
  (`src/motion.ts`) — interactive components press, toggle and settle on named spring presets
  (the house spring `SPRING` is damping 18 / mass 1 / stiffness 320; see [Motion](#motion)), and
  spinners, pulses and indeterminate bars run procedural `Animated` loops. The `MobileSlider` is built on
  `PanResponder` — React Native core dropped `Slider`, and the community package is a native
  module that would force every consumer to rebuild.

### The chart exception

The chart family is the one group of modules that takes dependencies. `MobileChartScatter`,
`MobileChartBar` and `MobileChartLine` render through
[`victory-native`](https://nearform.com/open-source/victory-native/) on top of Skia, because real
curve interpolation, UI-thread gestures and pan/zoom are not things a hand-rolled view tree does
well; `MobileChartPie` draws straight through Skia (victory-native's polar support is its
shakiest corner). `MobileSparkline` is the exception inside the exception: plain `Animated`, no
Skia.

| Package | Why it is needed |
|---|---|
| `victory-native` | the chart primitives — `CartesianChart`, `Scatter` |
| `@shopify/react-native-skia` | the renderer victory-native draws through |
| `react-native-reanimated` | the press state and animated paths run on the UI thread |
| `react-native-gesture-handler` | the gesture layer underneath reanimated |

All four are declared as **optional peer dependencies**, so the package installs and works without them and nothing else in it pulls them in. Install them only if you render a chart:

```bash
npx expo install @shopify/react-native-skia react-native-reanimated react-native-gesture-handler
pnpm add victory-native
```

Axis tick labels are drawn through Skia rather than React Native, so the Cartesian charts (`MobileChartScatter`, `MobileChartBar`, `MobileChartLine`) need a Skia font from `useFont()` and take it as the `font` prop. With no font the data still renders — only the labels are missing. The font is a prop rather than a bundled asset on purpose: shipping a `.ttf` would force every consumer to carry a font file it may not want, and would stop the charts matching the app's own typeface.

The only other non-obvious dependency is `react-native-safe-area-context`, which `apps/mobile` already
used before the package needed it.

## Icons in the showcase

`packages/mobile` ships no icon dependency, so `apps/mobile` picks its own. It uses
[Heroicons](https://heroicons.com) drawn with `react-native-svg` — the SVG route rather than an icon font.

```bash
npx expo install react-native-svg
pnpm --filter mobile add react-native-heroicons
```

Four reasons this route, and not a font:

- **`@expo/vector-icons` is being retired.** Expo now recommends migrating to the
  `@react-native-vector-icons/*` font packages, which work in Expo Go, dev builds and every platform.
  Heroicons has no package in that scope, so the showcase takes the SVG route instead — the same
  destination, a different mechanism.
- **No native rebuild.** `react-native-svg` is *included in Expo Go*, so nothing here needs a development
  build. Use `npx expo install` so the SDK-compatible version is picked — do not hand-pick one.
- **No font loading at all.** Nothing is added to the `expo-font` config plugin, so the icon-font conflict
  that the Expo migration guide warns about cannot arise.
- **Per-icon imports.** `apps/mobile/src/showcase/icons.tsx` imports one module per icon, by deep path. The
  package's barrel (`react-native-heroicons/outline`) re-exports all 324 icons from a single module and the
  package declares no `exports` map, so importing from the barrel would ship the entire set.

Every icon is drawn by one component, `ShowcaseIcon`, which maps a semantic name (`"trash"`, `"search"`) to
a glyph and reads its colour from `useMobileTheme()`. Nothing outside `icons.tsx` names a Heroicons
component, so the set — or the style, outline versus solid — is swappable in one file.

<Callout type="warn" title="Heroicons has no brand logos">
Tailwind excludes brand marks from the set, so there is no Apple, Google, GitHub or WeChat glyph. The
federated sign-in rows are therefore label-only, which is also why `MobileSocialProvider.icon` stays
optional. Real brand marks need a different source — they are not in any general-purpose UI icon set.
</Callout>
