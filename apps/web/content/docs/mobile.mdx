`@celestia-project/mobile` is the native counterpart to `@celestia-project/ui`: a component
library for Expo apps that renders **real platform views** — SwiftUI on iOS, Jetpack Compose on
Android — through `@expo/ui`, rather than emulating them in JavaScript.

<Callout type="info" title="Looking for the visual tour?">
This page is the technical reference — install, peer dependencies, platform support, API.
For the token ramp, the component index and a gallery of the screens, see the dedicated
**[Mobile showcase](/mobile)** surface.
</Callout>

It is not a port of the web library. The web components assume a DOM, hover states and a CSS
box model; the mobile components assume a thumb, a safe area and a touch target floor. What the
two packages share is the **taxonomy** (the same `primitive` / `composite` / `layout` split) and
the **design tokens**, so a component sits in the same mental bucket whichever library you are in.

<Callout type="info" title="Routing- and data-agnostic by contract">
Every component here is presentational: props in, callbacks out. There is no navigation library,
no data fetching, and no auth client. The host app owns routing, data and session state — which is
why this package has no dependency on `apps/api` and can be dropped into any Expo project.
</Callout>

## Running the showcase

`pnpm mobile` starts the Metro dev server for `apps/mobile`. The root script is
`turbo dev --filter=mobile`, which resolves to the package's `dev` script (`expo start`); Turbo
auto-detects the `expo` framework and `turbo.json` marks `dev` persistent and uncached, so it stays
attached like any other dev server. Metro itself is platform-agnostic — you pick a target after it
boots, or ask for one up front:

| Command | Target | Status |
|---------|--------|--------|
| `pnpm mobile` | Metro only — press `i`, `a` or `w` in the terminal | — |
| `pnpm --filter mobile ios` | iOS simulator or device (`expo start --ios`) | Supported |
| `pnpm --filter mobile android` | Android emulator or device (`expo start --android`) | Supported |
| `pnpm --filter mobile web` | Browser (`expo start --web`) | Supported — see [Platform support](#platform-support) |

Each target needs its own toolchain: Xcode and a booted simulator for iOS, the Android SDK and a
running emulator for Android. Web needs nothing beyond the three packages listed under
[Enabling web](#enabling-web).

`@expo/ui` is **included in Expo Go**, so the real SwiftUI and Compose views run in the sandbox
client with no native build at all — scan the QR code from `pnpm mobile` and the showcase opens on
a physical device. A development build (`npx expo run:ios` / `npx expo run:android`) is only
needed once you add native code of your own.

```bash
# Typecheck just the library
pnpm --filter @celestia-project/mobile typecheck
```

## Platform support

The library targets **iOS, Android and web**. The native platforms get real SwiftUI and Jetpack
Compose views through `@expo/ui`; web is served by `@expo/ui`'s **universal** entry, which is what
every component in this package imports.

| | iOS | Android | Web |
|---|-----|---------|-----|
| Components built on `@expo/ui` | ✅ SwiftUI | ✅ Compose | ✅ DOM equivalents |
| Rest of the package (plain React Native) | ✅ | ✅ | ✅ via `react-native-web` |
| `apps/mobile` showcase | ✅ | ✅ | ✅ |

`@expo/ui@57` exposes three entry points, and *which one you import* decides whether web works:

| Import | Implementation |
|--------|----------------|
| `@expo/ui` | **Universal** — resolves to `.ios.tsx` / `.android.tsx` / a generic DOM implementation |
| `@expo/ui/swift-ui` | iOS only |
| `@expo/ui/jetpack-compose` | Android only |

Every component in `packages/mobile` imports from `"@expo/ui"` — the universal entry — and never
from `/swift-ui` or `/jetpack-compose`. The universal implementations are real rather than stubs:
`Host` renders a plain `View`, `Switch` builds a DOM switch, `List` and `ListItem` use plain React
Native primitives, and `BottomSheet` renders through [`vaul`](https://vaul.emilkowal.ski/).

The rest of the chain is web-clean as well. `react-native-safe-area-context` resolves through
`react-native-web`; `expo-haptics` — which every interactive component calls — ships a no-op
`ExpoHaptics.web.ts`, so haptics simply do nothing in a browser; `expo-status-bar` ships
`StatusBar.web.js`; and `react-native-svg`, which the showcase icons are drawn with, ships a web
build. Each animation guards its driver with `Platform.OS !== "web"` (`button.tsx`,
`icon-button.tsx`, `skeleton.tsx`, `toast.tsx`, `progress.tsx`, `segmented-control.tsx`), and
`screen.tsx` puts the iOS-only `padding` keyboard behind a `Platform.OS === "ios"` check.

### Enabling web

`apps/mobile` needs three packages for the browser target; `expo install` picks the SDK-compatible
versions:

```bash
npx expo install react-native-web react-dom @expo/metro-runtime
```

and `app.json` has to declare the web bundler:

```json
"web": { "bundler": "metro", "output": "single" }
```

Both are already in place, so `pnpm --filter mobile web` serves the showcase in a browser. Two
things to know:

- **Props marked `@platform ios` / `@platform android` are inert on web.** `MobileList`'s
  `onRefresh` is the one in this package: the prop is accepted and ignored, because there is no
  native refresh affordance to show.
- **Web is a preview surface, not a port.** The DOM rendering comes from `@expo/ui` and
  `react-native-web`, so it is close to, but not pixel-identical with, the SwiftUI / Compose
  rendering. When a feature needs a first-class web implementation, use `@celestia-project/ui`;
  the two libraries share design tokens and the primitive / composite / layout taxonomy precisely
  so that the same screen can have a native and a browser implementation.

<Callout type="info" title="Publishing">
`@celestia-project/mobile` is part of the npm publish set: `scripts/publish.sh` publishes
`@celestia-project/ui`, `@celestia-project/create` and `@celestia-project/mobile`. Inside the
workspace the package is consumed from source through the workspace protocol
(`"@celestia-project/mobile": "workspace:*"`). Publish it standalone with `pnpm publish:mobile`,
or all packages together with `pnpm publish:packages`.
</Callout>

## Installation

Inside a workspace app the package resolves from the workspace protocol:

```bash
pnpm --filter mobile add @celestia-project/mobile@workspace:*
```

The native dependencies are peer dependencies and must be installed by the app, because they
contain platform code that Expo has to autolink:

```bash
npx expo install @expo/ui expo-haptics react-native-safe-area-context
```

Pin `react-native` to the version Expo SDK 57 pairs with (`0.86.3`) — `npx expo install
react-native` resolves it. Do not bump to `^0.87` manually: Expo 57's Metro tooling requires
`rn-get-polyfills`, which React Native 0.87 removed.

| Peer dependency | Required by | Notes |
|-----------------|-------------|-------|
| `@expo/ui` | `MobileSwitch`, `MobileList`, `MobileBottomSheet`, `MobileHost` | Real SwiftUI / Compose views |
| `expo-haptics` | Every interactive component | Same-frame tactile feedback |
| `react-native-safe-area-context` | `MobileScreen` and everything built on it | Safe-area insets |
| `react` / `react-native` | — | React 19, RN 0.86.3 (Expo SDK 57) |

## Component categories

Components are grouped by **role**, not by atomicity — the same rule `@celestia-project/ui` uses,
so the two libraries read the same way.

| Category | Directory | What belongs here | Rule of thumb |
|----------|-----------|-------------------|---------------|
| **primitive** | `src/components/primitive/` | Generic building blocks. Each wraps one native control or one plain surface. | *"Would I reach for this in any app?"* |
| **composite** | `src/components/composite/` | Opinionated assemblies built from primitives. | *"Is this a `<Primitive>` with a specific job?"* |
| **layout** | `src/components/layout/` | Full-screen shells and screens. Own the frame; take content through slots. | *"Does it own the whole screen?"* |

<Callout type="note" title="“Primitive” means generic, not atomic">
`MobileCard` ships `MobileCardHeader`, `MobileCardTitle`, `MobileCardDescription`,
`MobileCardContent` and `MobileCardFooter` — and is still a primitive, exactly as `Card` is in
`@celestia-project/ui/primitive`. A compound component is not automatically a composite; only an
*opinionated* one is.
</Callout>

## Setup

`MobileHost` bridges React Native to the native layer and provides the theme context every
component reads.

<Callout type="warn" title="MobileHost must be given a size">
`MobileHost` renders `@expo/ui`'s `Host`, whose `matchContents` and `useViewportSizeMeasurement`
props both default to `false`. An **unsized host lays out to zero height**, so every child
collapses with it and the app renders as a blank screen — the root view's background, and nothing
else. `style={{ flex: 1 }}` is the fix, and it is not optional.

Reach for `useViewportSizeMeasurement` instead when the host should size to the available viewport,
or `matchContents` when it should shrink to fit its content.
</Callout>

`SafeAreaProvider` must sit above it so `MobileScreen` can resolve insets, and
`MobileToastProvider` must sit inside a **sized** parent, because its overlay positions itself
absolutely against that parent.

```tsx
import * as React from "react"
import { View } from "react-native"
import { SafeAreaProvider } from "react-native-safe-area-context"
import { MobileHost, MobileToastProvider } from "@celestia-project/mobile"

export default function App() {
  return (
    <SafeAreaProvider>
      <MobileHost style={{ flex: 1 }}>
        <View style={{ flex: 1 }}>
          <MobileToastProvider>{/* your navigator / screens */}</MobileToastProvider>
        </View>
      </MobileHost>
    </SafeAreaProvider>
  )
}
```

Pass `forcedTheme="light" | "dark"` to `MobileHost` to override the device preference — the
showcase uses this for its theme toggle.

```tsx
      />

  )

```

## Screens

The `layout` category is where this package diverges most from the web one. A screen owns the
whole frame — safe area, scrolling, keyboard avoidance, header, pinned footer — and takes its
content through slots.

### The shell + thin-screen split

`MobileScreen` is the base frame. `MobileAuthShell` adds the logo / heading / form / aside /
footer arrangement that all five auth screens share. Each auth screen then supplies **only** its
own fields and defaults:

```tsx
import { MobileSignInScreen } from "@celestia-project/mobile"

export default function SignIn() {
  const [error, setError] = React.useState<string>()
  const [loading, setLoading] = React.useState(false)

  return (
    <MobileSignInScreen
      error={error}
      loading={loading}
      socialProviders={[
        { id: "google", label: "Google" },
        { id: "apple", label: "Apple" },
      ]}
      onForgotPassword={() => router.push("/forgot-password")}
      onSignUp={() => router.push("/sign-up")}
      onSubmit={async ({ email, password }) => {
        setLoading(true)
        setError(undefined)
        try {
          await auth.signIn(email, password)
          router.replace("/")
        } catch (cause) {
          setError(cause instanceof Error ? cause.message : "Sign-in failed.")
        } finally {
          setLoading(false)
        }
      }}
    />
  )
}
```

The screen owns its **field** state and reports the result; it never authenticates, stores a
session or navigates. Server errors arrive back through `error`, which is why the same screen
works for a credential rejection, a network failure and an offline queue.

### Building a new screen

A new screen that resembles an existing one **composes the shell** — it never re-implements the
header. That is what stops six auth screens from drifting apart:

```tsx
import * as React from "react"
import { MobileAuthShell, MobileButton, MobileFormField, MobileTextInput } from "@celestia-project/mobile"

export function ChangeHandleScreen({ onSave }: { onSave: (handle: string) => void }) {
  const [handle, setHandle] = React.useState("")

  return (
    <MobileAuthShell
      heading="Choose a handle"
      subheading="This is how others will find you."
      onBack={() => history.back()}
    >
      <MobileFormField label="Handle" required>
        <MobileTextInput
          value={handle}
          onChangeText={setHandle}
          autoCapitalize="none"
          autoCorrect={false}
        />
      </MobileFormField>

      <MobileButton onPress={() => onSave(handle)}>Save</MobileButton>
    </MobileAuthShell>
  )
}
```

For a screen with no auth framing, compose `MobileScreen` directly and drive the header through
props — it renders a `MobileNavBar` as soon as you pass `title`, `onBack` or either header slot:

```tsx
<MobileScreen title="Reports" onBack={goBack} largeTitle>
  {/* content */}
</MobileScreen>
```

<Callout type="tip" title="Onboarding and settings">
`MobileOnboardingScreen` takes a `slides` array and handles paging, the page indicator and the
skip / next / get-started actions. `MobileSettingsScreen` takes `MobileSettingsSection` groups and
inserts the row separators for you — so a stray divider after the last row is impossible.
</Callout>

## Design rules

Every component in this package follows the same non-negotiables. They are enforced by
convention and review, not by a linter, so they are worth knowing before adding a component:

1. **No hardcoded colours.** Everything reads `useMobileTheme()`; the light and dark ramps are both complete.
2. **44×44pt minimum touch target** on every interactive element (`metrics.minTouchTarget`). A control drawn shorter to match the web design system — `MobileButton` is 32px — meets the floor with `hitSlop` rather than by inflating the box.
3. **Haptics fire on the causal commit frame** — `Light` for normal presses, `Medium` for destructive, `selectionAsync` for toggles. Never on mount.
4. **16px font floor** on text inputs, to prevent OS viewport zoom.
5. **Tabular numerals** for counters, prices and timers.
6. **Icons arrive as props.** The package takes no icon dependency; only structural marks (a tick, a chevron, a magnifier) may be drawn inline. The showcase app is the consumer side of that rule and supplies its own set — see [Icons in the showcase](#icons-in-the-showcase).
7. **No hover-only affordances.**
8. **Forms never disable the submit button for empty fields.** It stays pressable and names what is missing; it is disabled only while loading.
9. **Screens are presentational.** Props in, callbacks out — no fetching, no auth client, no routing.
10. **Text children are wrapped; composed children are not.** `MobileButton`, `MobileBadge`, `MobileLink`, `MobileCardTitle` and `MobileCardDescription` route their children through `isTextChildren()` (`src/utils.ts`) to decide whether to wrap them in `MobileText`. Never replace it with `typeof children === "string"` or `React.isValidElement(children)`: JSX turns any element with more than one child into an **array** (`+{count}%` becomes `["+", count, "%"]`), and both of those checks mis-classify that array — the first renders bare strings outside a `<Text>` and the second nests a `<View>` inside one. Either way the app crashes at render.

## Dependencies

The package adds **no runtime dependencies of its own** — with one declared exception. Two deliberate consequences:

- **Paging** uses `ScrollView` + `pagingEnabled`, not `reanimated` or `gesture-handler`.
- **Motion** uses React Native's built-in `Animated`, and the `MobileSlider` is built on `PanResponder` — React Native core dropped `Slider`, and the community package is a native module that would force every consumer to rebuild.

### The chart exception

`MobileChartScatter` is the one module that takes dependencies. It renders through [`victory-native`](https://nearform.com/open-source/victory-native/) on top of Skia, because real curve interpolation, UI-thread gestures and pan/zoom are not things a hand-rolled view tree does well.

| Package | Why it is needed |
|---|---|
| `victory-native` | the chart primitives — `CartesianChart`, `Scatter` |
| `@shopify/react-native-skia` | the renderer victory-native draws through |
| `react-native-reanimated` | the press state and animated paths run on the UI thread |
| `react-native-gesture-handler` | the gesture layer underneath reanimated |

All four are declared as **optional peer dependencies**, so the package installs and works without them and nothing else in it pulls them in. Install them only if you render a chart:

```bash
npx expo install @shopify/react-native-skia react-native-reanimated react-native-gesture-handler
pnpm add victory-native
```

Axis tick labels are drawn through Skia rather than React Native, so `MobileChartScatter` needs a Skia font from `useFont()` and takes it as the `font` prop. With no font the dots still plot — only the labels are missing. The font is a prop rather than a bundled asset on purpose: shipping a `.ttf` would force every consumer to carry a font file it may not want, and would stop the chart matching the app's own typeface.

The only other non-obvious dependency is `react-native-safe-area-context`, which `apps/mobile` already
used before the package needed it.

## Icons in the showcase

`packages/mobile` ships no icon dependency, so `apps/mobile` picks its own. It uses
[Heroicons](https://heroicons.com) drawn with `react-native-svg` — the SVG route rather than an icon font.

```bash
npx expo install react-native-svg
pnpm --filter mobile add react-native-heroicons
```

Four reasons this route, and not a font:

- **`@expo/vector-icons` is being retired.** Expo now recommends migrating to the
  `@react-native-vector-icons/*` font packages, which work in Expo Go, dev builds and every platform.
  Heroicons has no package in that scope, so the showcase takes the SVG route instead — the same
  destination, a different mechanism.
- **No native rebuild.** `react-native-svg` is *included in Expo Go*, so nothing here needs a development
  build. Use `npx expo install` so the SDK-compatible version is picked — do not hand-pick one.
- **No font loading at all.** Nothing is added to the `expo-font` config plugin, so the icon-font conflict
  that the Expo migration guide warns about cannot arise.
- **Per-icon imports.** `apps/mobile/src/showcase/icons.tsx` imports one module per icon, by deep path. The
  package's barrel (`react-native-heroicons/outline`) re-exports all 324 icons from a single module and the
  package declares no `exports` map, so importing from the barrel would ship the entire set.

Every icon is drawn by one component, `ShowcaseIcon`, which maps a semantic name (`"trash"`, `"search"`) to
a glyph and reads its colour from `useMobileTheme()`. Nothing outside `icons.tsx` names a Heroicons
component, so the set — or the style, outline versus solid — is swappable in one file.

<Callout type="warn" title="Heroicons has no brand logos">
Tailwind excludes brand marks from the set, so there is no Apple, Google, GitHub or WeChat glyph. The
federated sign-in rows are therefore label-only, which is also why `MobileSocialProvider.icon` stays
optional. Real brand marks need a different source — they are not in any general-purpose UI icon set.
</Callout>

## Status

<Callout type="warn" title="Not yet verified on a device">
The library is typechecked end to end (package and showcase app) and the showcase Metro-bundles
into a working Hermes bundle (`npx expo export --platform ios`) and a working web bundle
(`npx expo export --platform web`, 506 modules). It has **not been run on a simulator or device**
in this workspace — the machine has no Xcode, so `@expo/ui`'s real native views and gesture
behaviour cannot be exercised headlessly.

Three things need a device before this is trusted: the whole package end to end; `MobileSlider`'s
gesture geometry in particular — a `PanResponder` cannot be validated by a typecheck; and the showcase
icons, where optical size, stroke weight and vertical alignment inside a 44pt control are all things a
typecheck cannot see.
</Callout>
