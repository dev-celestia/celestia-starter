The `packages/` directory contains shared workspace packages. Some are private workspace-only packages (`@workspace/*`), others are published to npm under the `@celestia-project` org.

## @celestia-project/ui

[![npm](https://img.shields.io/npm/v/@celestia-project/ui)](https://www.npmjs.com/package/@celestia-project/ui)

A shadcn-style React component library built on **Base UI** and **Tailwind CSS v4**, with 126 components.

**Exports:**

| Import path | Resolves to |
|-------------|-------------|
| `@celestia-project/ui` | Barrel export of every component (tree-shaken) |
| `@celestia-project/ui/globals.css` | Global styles and CSS variables |
| `@celestia-project/ui/primitive/*` | Primitive components (button, card, input, label) |
| `@celestia-project/ui/composite/*` | Composite components (field, sidebar, data-table) |
| `@celestia-project/ui/components/ai/*` | AI chat & agent components |
| `@celestia-project/ui/hooks/*` | Shared React hooks |
| `@celestia-project/ui/lib/*` | Utilities (`cn` helper) |

**Usage:**

```tsx
import { Button } from "@celestia-project/ui"
import { Button } from "@celestia-project/ui/primitive/button"
import { cn } from "@celestia-project/ui/lib/utils"
```

**Key dependencies:** `@base-ui/react`, `class-variance-authority`, `tailwind-merge`, `next-themes`, `@phosphor-icons/react`

### Using it outside this monorepo

The package is published to npm and can be installed in any React 19 + Tailwind CSS v4 project:

```bash
pnpm add @celestia-project/ui
```

#### Integration Option A: Quickstart (All-in-one)

Import the global stylesheet in your app entry point (`app/layout.tsx` or `globals.css`):

```tsx
import "@celestia-project/ui/globals.css";
```

#### Integration Option B: Existing Tailwind v4 App (`@source` directive)

If your app already has an existing Tailwind v4 setup and custom theme variables, add the `@source` directive in your main CSS file so Tailwind scans the package without double-importing or overriding styles:

```css
@import "tailwindcss";
@source "../../node_modules/@celestia-project/ui";
@source "../**";

@custom-variant dark (&:is(.dark *));
```

See the [Components docs](/docs/components) and the [npm package](https://www.npmjs.com/package/@celestia-project/ui) for details.

## @celestia-project/alpine-ui

[![npm](https://img.shields.io/npm/v/@celestia-project/alpine-ui)](https://www.npmjs.com/package/@celestia-project/alpine-ui)

Component primitives built on **Alpine.js** and **Tailwind CSS v4** — referenced and cloned from `@celestia-project/ui`.

**Exports:**

| Import path | Resolves to |
|-------------|-------------|
| `@celestia-project/alpine-ui` | Barrel export of all primitives, class utilities, and Alpine plugin |
| `@celestia-project/alpine-ui/globals.css` | Global styles and Tailwind CSS v4 setup |
| `@celestia-project/alpine-ui/plugin` | `alpineUI(Alpine)` plugin registering Alpine `Alpine.data(...)` stores |

**Usage:**

```typescript
import Alpine from "alpinejs"
import { alpineUI } from "@celestia-project/alpine-ui"

Alpine.plugin(alpineUI)
Alpine.start()
```

## @celestia-project/create

[![npm](https://img.shields.io/npm/v/@celestia-project/create)](https://www.npmjs.com/package/@celestia-project/create)

The interactive CLI that scaffolds a new Celestia Starter project. Lives in `packages/cli`.

**Usage:**

```bash
npx @celestia-project/create my-app
npx @celestia-project/create my-app --features auth,dashboard
```

**Bin registered:** `create-celestia`

**Publishing:**

```bash
# From the monorepo root — publishes both @celestia-project/ui and @celestia-project/create
pnpm publish:packages

# Dry run first (previews tarball contents without uploading)
pnpm publish:dry-run
```

See the [CLI docs](/docs/cli) for the full feature flag reference and local testing guide.

## @workspace/feature-manager

A CLI and runtime registry that discovers, installs, and tracks features defined by `feature.json` manifests under the project's `features/` directory.

**CLI commands (via root scripts):**

```bash
pnpm add-feature <name>       # Install (or --force reinstall/upgrade) a feature
pnpm remove-feature <name>    # Uninstall a feature, restoring shared files
pnpm list-features            # List available and installed features
pnpm verify-features [name]   # Check installed features for drift or breakage
pnpm prompt-feature <name>    # Generate the AI verification prompt
```

Common flags: `--dry-run` (plan only, writes nothing), `--force` (reinstall/upgrade,
or override removal safety checks), `--strict` (treat warnings as errors),
`--json` (machine-readable report), `--quiet`.

**How `add` works:**

1. Reads `features/<name>/feature.json` (legacy v1 manifests using `files` are normalized)
2. Validates it — malformed fields and paths that escape the repository are rejected
   before anything is written
3. Verifies `requires` against the tracker (root `features.json`)
4. Plans every action, then snapshots each path it will touch
5. Copies `copies` entries into the workspace — `apps/api`, `apps/web`, `packages/*`, root files
6. Inserts `insertions` snippets into managed marker regions
7. Applies `jsonAppends` to JSON arrays (e.g. the docs sidebar `meta.json`)
8. Merges `dependencies` / `devDependencies` into each target package's `package.json`,
   reporting any version conflict instead of silently replacing it
9. Records the feature, its files (with content hashes), backups and dependency
   changes in the tracker, then prints next steps (`pnpm install`, env vars,
   `postInstall` commands)

If any step fails, every touched path is rolled back — a failed install can never
leave a half-applied repository behind.

**Shared files:** when two features provide the same path (for example the CMS
media dialog, provided by `cms`, `media-r2` and `unsplash`), the newest install
wins and the previous content is backed up under `.feature-manager/backups/`.
Removing a feature restores the previous owner's version rather than deleting the
file. Files you edited after installing are kept unless `--force` is given.

**Feature manifest schema (`feature.json`):**

```json
{
  "name": "blog",
  "version": "1.0.0",
  "description": "Full CRUD blog over the typed RPC client",
  "requires": ["auth", "dashboard"],
  "copies": [
    { "from": "api/src/features/blog/routes.ts", "to": "apps/api/src/features/blog/routes.ts" }
  ],
  "insertions": [
    { "file": "apps/api/src/app.ts", "marker": "routes", "snippet": "snippets/api-routes.ts" }
  ],
  "jsonAppends": [
    { "file": "apps/web/content/docs/meta.json", "path": "pages", "value": "blog" }
  ],
  "dependencies": { "apps/api": { "drizzle-orm": "^0.45.2" } },
  "env": { "apps/api": ["DATABASE_URL=postgresql://postgres:postgres@localhost:5432/celestia"] },
  "postInstall": ["pnpm --filter @workspace/db db:push"],
  "notes": "Optional post-install instructions"
}
```

### Managed marker regions

Insertions target empty sentinel regions that already exist in shared files. Installing wraps the snippet in a per-feature block so it can later be replaced (idempotent reinstall) or removed cleanly:

```ts
// feature-manager:<marker>:begin
// feature-manager:<marker>:<feature>:begin
...snippet...
// feature-manager:<marker>:<feature>:end
// feature-manager:<marker>:end
```

Available regions:

| Marker | File | What features insert |
|--------|------|----------------------|
| `imports` | `apps/api/src/app.ts` | Route module imports |
| `routes` | `apps/api/src/app.ts` | `.route(...)` mounts |
| `auth-imports` | `apps/api/src/auth.ts` | Better Auth server-plugin imports |
| `auth-plugins` | `apps/api/src/auth.ts` | Plugin entries in the `plugins` array |
| `tables` | `packages/db/src/schema.ts` | Drizzle tables + relations |
| `user-fields` | `packages/db/src/schema.ts` | Additional columns on the `user` table |
| `imports` | `apps/web/components/dashboard/sidebar.tsx` | Icon imports |
| `nav` | `apps/web/components/dashboard/sidebar.tsx` | Sidebar navigation items |
| `nav-visibility` | `apps/web/components/dashboard/sidebar.tsx` | Per-item visibility filter inside the nav map |
| `client-imports` | `apps/web/lib/auth-client.ts` | Better Auth client-plugin imports |
| `client-plugins` | `apps/web/lib/auth-client.ts` | Client-plugin entries in the `plugins` array |
| `cards` | `apps/web/content/docs/index.mdx` | Landing page `<Card>` links |
| `features` | `README.md` | "Installed Features" bullets |

Marker ids are scoped per file, so `imports` in `app.ts` and `imports` in `sidebar.tsx` don't collide. Comment syntax follows the file type (`//` for TS/TSX, `<!-- -->` for `.md`, `{/* */}` for `.mdx`). Files that cannot carry comments (e.g. `meta.json`) use `jsonAppends` instead.

**Authoring snippets:**

- Snippets are inserted verbatim — include their leading indentation in the snippet file itself (only the sentinel comments are auto-indented)
- A single trailing newline is stripped before insertion

**Programmatic exports:**

| Import path | Purpose |
|-------------|---------|
| `@workspace/feature-manager` | Everything below, re-exported from one entry point |
| `@workspace/feature-manager/markers` | Marker engine: `insertIntoRegion`, `removeFromRegion`, `hasRegion`, `listRegionFeatures`, `jsonAppend`, `jsonRemove` |
| `@workspace/feature-manager/manifest` | `loadManifest`, `normalizeManifest`, `validateManifest`, `discoverFeatures` |
| `@workspace/feature-manager/installer` | `planInstall`, `executeInstall`, `installFeature` |
| `@workspace/feature-manager/remover` | `planRemove`, `executeRemove`, `removeFeature` |
| `@workspace/feature-manager/verifier` | `verify` — integrity report for installed features |
| `@workspace/feature-manager/types` | `Feature`, `FeatureManifest`, `FeatureCopy`, `FeatureInsertion`, `FeatureTracker` types |
| `@workspace/feature-manager/registry` | Runtime feature registry |

All of these take an explicit repo `root`, so they can be driven from scripts and
tests rather than only from the CLI.
